## 1. 结论先行

已确认采用 **B 方案：Next.js UI/BFF + TypeScript/Node.js Agent Worker（LangGraph.js）** 的模块化单体架构。Next.js 持有身份、学习画像、规划、内容、测评和实践等核心业务聚合；Agent Worker 独立部署、不暴露公网，只负责编排、模型调用与受控工具，通过版本化 OpenAPI/JSON Schema 与核心服务通信。

**2026-09-16 决策变更：**原 A 方案（Python FastAPI/LangGraph Agent Worker）已废弃。变更理由不是“Python 做不到”，而是**面向数千到数万用户的长期规模，TypeScript 每单位并发所需的内存与 CPU 更少，并且能把双栈合并为单栈**（详见 [09-全栈TypeScript迁移方案](./09-全栈TypeScript迁移方案.md) 第 2 节）。原先为 Python 保留的文档解析、OCR、RAG 评测等生态理由，在本产品当前范围内没有已确认的需求；未来若确实需要，必须以 TypeScript 或独立服务单独立项，不得据此恢复 Python Agent 编排。

性能瓶颈仍应通过队列、缓存、检索评测、模型预算和异步任务治理解决，而不是依赖语言更换。

### 托管模型 API 采用前提

> **流式与结构化输出约束：**所有真实生成请求固定使用 `stream=true`，由 Agent Worker 的安全出网层以 SSE 读取 Provider 返回；Worker 仅在收到完成标记、聚合完整内容并通过大小限制后，才进入结构化解析与业务校验。题集等要求 JSON 的任务在请求载荷中同时设置 `response_format: {"type": "json_object"}`，并使用顶层 JSON 提示词；Pydantic 校验失败时走一次受控修复。浏览器侧订阅的是 AgentRun 状态/事件，而不是未经校验的模型 JSON 片段。

MVP 不在本地或 Docker 中运行大模型，因此不需要 GPU、模型权重缓存、显存预算或推理服务运维。生成调用采用用户 BYOK：用户保存 OpenAI-compatible Base URL、API Key 和模型名，并承担该 Provider 的费用；平台负责超时、限流、重试、结构化校验和可观测性。API Key 以 AES-256-GCM 加密保存，浏览器仅能写入或覆盖，不能再次读取。未来有稳定 GPU 基础设施、持续并发和明确成本收益后，才重新评估加入 vLLM；当前不把它放入实现或 Compose 范围。

### 为什么放弃 Python Agent 边界（2026-09-16 决策变更）

原判断是“把高变化、长耗时的 Agent 编排隔离到 Python，以便承接文档解析、OCR、RAG 评测与数据处理生态”。该判断在**长期规模**下不再成立，理由有三点：

1. **单位并发的成本**：Python 侧当前为 Celery prefork 池，“一个并发 = 一个进程”（各自加载 SQLAlchemy、httpx、pydantic、cryptography 等模块）；Node 中“一个并发 = 一个 async 任务”。面向数千到数万用户（峰值数百并发）时，这个差异直接决定机器数量与成本。
2. **单位运行的 CPU 成本**：SSE 逐块 JSON 解析、结构化输出校验、字符串处理与解密等 CPU 工作，V8 的单位耗时低于解释执行的 CPython（Pydantic v2 与 orjson 已缓解校验与序列化，但业务逻辑仍是解释执行）。
3. **单语言栈的长期成本**：双栈意味着两套运行时、两套 CI、两套依赖锁与 OpenAPI/JSON Schema ↔ Pydantic/Zod 的双向手工对齐；合并后这些成本消失，且可共用类型、契约与表定义。

同时明确两条不成立的表述，避免后续设计建立在错误前提上：Python 的 I/O 并发能力（asyncio/epoll）与 Node 属同一量级，**不能**以“Python I/O 弱”为理由；Node 主线程同样是单线程，**不能**以“TS 更擅长 CPU”为理由省略 `worker_threads` 隔离、限流与背压。

该边界变更后仍然坚持以下约束：

- Agent 只能通过 Core API/ACL 和明确的 ports 读取或改变学习业务；不能直接改 `learning_plans`、`assessments` 等核心表。
- 所有 Agent 命令异步化，使用 `agent_run_id`、幂等键、graph/prompt 版本；Core API 负责授权、事务和状态机。
- OpenAPI/JSON Schema 在 CI 中做破坏性变更检查。
- Agent Worker 内部按 `workflows`、`tools`、`infrastructure` 分层；任何未来的解析器或数据处理器只能作为可替换适配器，不能把其数据模型泄漏到 Learning Content 领域层。
- **不保留 Python 运行时**：若未来确认需要文档解析、OCR 或评测能力，须以 TypeScript 或独立服务单独立项，不得据此恢复 Python Agent 编排。

### 方案选择记录（B 已确认，2026-09-16 变更）

| 方案 | 优点 | 代价 | 适用判断 |
| --- | --- | --- | --- |
| A. Next.js BFF + Python Agent Worker | 保留 Next.js 全栈开发体验；Python 的解析、RAG 与评测生态更适合资料密集场景 | 两套运行时与双 CI；每并发的内存与 CPU 成本更高 | **已废弃（2026-09-16）**：在面向数千到数万用户的长期规模下不再划算 |
| **B. Next.js + TypeScript/Node.js Agent Worker（LangGraph.js）** | 单语言栈、共享类型与契约；单位并发的内存与 CPU 成本更低，扩展成本可控 | 需要重建安全出网、MCP 适配与四个工作流，安全出网 PoC 是硬门禁 | **当前实施方案**，见 [09-全栈TypeScript迁移方案](./09-全栈TypeScript迁移方案.md) |
| C. Next.js + 独立 Python Core API + Python Agent | 领域层与 Agent 都在 Python，边界清晰 | 前端、Core API、Agent 三个进程；首版运维和契约成本最高 | 不纳入当前方案 |

无论选择哪一行，**领域模型只保留一份、Agent 通过 AgentRun 异步执行、代码 Demo 以可版本化内容产物保存**这三条不变。在线代码执行仅在 P1 增加，并独立隔离。

本文所说的 `Core API` 在 MVP 中就是 Next.js 的 Route Handler/BFF 加 `src/modules/*` 应用服务，不另起一个 Node API 进程；当接口规模或团队边界需要时，再按 DDD 文档的迁移路线抽成独立服务。

### 进程职责

> **迁移期说明：**下列为目标职责。迁移完成前，Python 侧的 `agent-dispatcher` 与 `agent-celery-worker` 与 TypeScript Worker 并存，由 Dispatcher 按 `run_type` 路由，同一个 AgentRun 只属于一个运行时（见 [09-全栈TypeScript迁移方案](./09-全栈TypeScript迁移方案.md) 第 7 节）。原有的 FastAPI `agent-api` 进程在迁移中退役，其唯一健康检查由 TS Worker 的最小 `/health` 等价承接。

- `web`：渲染界面、会话、资源授权、核心领域 command/query、创建 `AgentRun`、通过 SSE 推送运行事件。不得在请求线程执行长时间 LLM 调用或用户代码。
- `agent-dispatcher`：使用 `FOR UPDATE SKIP LOCKED` 领取 `agent.run.requested` Outbox 事件，投递后回写 `published`；若在发送后中断允许重复投递。多实例必须各自配置唯一的 `locked_by`，并在收到终止信号时优雅关闭。
- `agent-worker`：消费队列，以 `agent_run_id` 作为任务幂等标识，维护 AgentRun 生命周期、协作式取消检查、超时和重试，执行工作流并经 Core API/ACL 请求领域写入。
- `model-provider`：用户选择的外部 OpenAI-compatible 生成 API，不是 Compose 服务；Web 与实际执行模型任务的 Worker 只持有凭据加密主密钥，Worker 按连接 ID 解密后负责超时、预算、重试和可审计 fallback；用户 API Key 不作为容器环境变量存在。
- `ingestion`：首版可作为 Agent Worker 内的受限模块，负责受控 URL/PDF/Markdown 获取、清洗、切块和嵌入，并通过 Content 的 application port/API 写入；数据量上升后拆成独立 Worker。**注意：**由于不再保留 Python 运行时，MinerU 等 Python 解析能力不可直接复用；若将来确认需要，必须以 TypeScript 实现或作为独立服务单独立项，不得因此恢复 Python Agent 编排。

Web 与 Agent 之间使用内部服务身份（短期 token/mTLS 或 HMAC），Agent 端点不暴露公网；Core API 负责用户授权和领域事务，Agent 不能以“工具调用”绕过这些检查。

## 3. 向量检索存储设计（P0 为 PostgreSQL + pgvector）

### 3.1 数据分工

PostgreSQL 是业务事实源，建议至少包含以下表（实际字段以领域模型为准）：

`users`、`learner_profiles`、`learning_goals`、`learning_plans`、`plan_nodes`、`content_sources`、`content_documents`、`content_chunks`、`assessments`、`assessment_items`、`assessment_attempts`、`assessment_answers`、`card_contents`、`agent_runs`、`agent_checkpoints`、`outbox_events`。P0 的本地 Demo 是 `card_contents` 的结构化内容，不读写 `code_runs`；当前物理 `code_runs` 表仅为 P1 预留。产品界面可把 `agent_runs` 展示为“学习运行”，但数据库和契约统一使用 `agent_run_id`。

- 领域状态使用明确列；模型原始响应、图状态和可演进元数据放入受控 `jsonb`，并记录 schema/version。
- 所有用户归属资源带 `owner_id`（未来多租户可增加 `tenant_id`），服务层每次查询都执行授权过滤；高隔离部署再启用 PostgreSQL RLS。
- 状态迁移通过事务完成；跨服务副作用写入 `outbox_events`，由 Dispatcher 投递到队列，避免“数据库已提交但任务未发送”。
- 原始网页/PDF放对象存储，表中保存 `source_uri`、内容哈希、抓取时间、解析器版本和版权/可见性信息。

### 3.2 向量检索约定

- Agent 的检索工作流只依赖 `application.ports.VectorStore`：`upsert`、`delete`、`search`。它可承载 dense 与 sparse 两类向量；单次 `search` 只查询一种模态，统一以“`score` 越高越相关”表示命中，不泄漏 pgvector 的 `<=>` 距离表达式、Milvus collection 或 SDK 类型。
- P0 仅实现 `PgvectorVectorStore`。未来 Milvus 仅作为 `MilvusVectorStore` 的替代适配器，不与 pgvector 双写，也不让领域模型直接依赖任一数据库。
- `content_chunks.embedding` 使用 `vector(n)`；`n` 由 embedding provider 配置决定，切换模型必须新建版本或重嵌入，不能混用维度。
- P0 先使用余弦距离精确检索；在数据量较小或频繁写入阶段不建 ANN 索引。达到检索 p95/内容量阈值并通过离线评测后，再建立 HNSW；索引参数（`m`、`ef_construction`、查询 `ef_search`）通过迁移和配置固定并压测。
- 查询先按 `owner_id`、来源类型、语言、技术栈、版本等 metadata 过滤，再做向量召回；P0 使用 dense 向量召回与 PostgreSQL FTS（`tsvector`）分别产出候选集，再由 `HybridRetriever` 以 RRF 融合排序，避免只靠语义相似度。FTS 是词法检索，不等同于 BGE-M3 的学习型 sparse embedding，但足以补足托管 Embedding API 仅返回 dense 向量的限制。
- 若未来接入能返回 sparse 向量的模型，`VectorStore` 可写入并单独检索 `SparseVector`；上层仍分别取得 dense、sparse、FTS 的排序列表后融合。ColBERT 多向量/MaxSim 是另一种检索表示，届时应新增专用端口或 reranker，而不是伪装为一个 sparse 向量。
- Agent 的 RAG 查询必须经 Content context 的 `RetrieverPort`/Core API（带用户归属和来源授权过滤），不得直接把 pgvector 表暴露给图节点或 UI；返回结果必须包含 `document_id`、`chunk_id` 和来源定位，供引用校验。
- 每个 chunk 保存 `embedding_model`、`embedding_version`、`chunker_version`、`token_count` 和来源定位（URL/页码/行号），生成内容必须返回可点击引用。
- 建立离线检索评测集（问题、期望来源、召回@k、引用正确率），不要以“主观感觉”决定索引或模型。

### 3.3 未来迁移 Milvus 的约束

Milvus 的价值主要在于大规模向量、并发索引和检索吞吐的扩展能力；它不会自动修复 embedding、分块、查询改写、metadata 过滤或重排序造成的低召回。pgvector 同样支持精确检索、HNSW 与 PostgreSQL 全文检索，P0 应先用离线评测定位质量问题。[pgvector 官方说明](https://github.com/pgvector/pgvector)

当压测证实 pgvector 已无法满足已确认的规模或延迟目标时，再向用户提交 Milvus 迁移方案：collection/metadata 映射、全量 backfill、离线 recall@k 与引用正确率对比、灰度双读、切换开关、成本估算和回滚步骤。Milvus 支持 ANN、metadata filtering、全文/混合检索与水平扩展，但这些能力须通过适配器和评测引入。[Milvus 官方概览](https://milvus.io/docs/overview.md)

### 3.4 连接、备份和迁移

- Web/Agent 使用各自的连接池；长任务不能占用 Core API 事务连接等待模型响应。Agent 直接连接数据库时只允许 AgentRun、运行事件与 Outbox 等基础设施访问，业务聚合必须经 Core API。面向数百并发时连接池必须按**事务并发**设置（而非按并发运行数），并保证总连接数在 PostgreSQL `max_connections` 预算之内。
- 生产启用自动备份、PITR、恢复演练和迁移前快照；开发环境用 Testcontainers/Compose 重建，不依赖手工改表。
- pgvector 版本、PostgreSQL 版本和 embedding 维度写入 `system_settings`/迁移元数据，并在启动健康检查中校验。

## 4. Agent 编排方案

### 4.1 图状态与节点

部署一个 Agent Worker，但在同一 Worker 内实现两个职责隔离的业务 Agent；它们不是两个常驻聊天服务，也不需要 Supervisor Agent：

1. **学习规划 Agent（Learning Architect）**：逻辑会话键为 `learning_architect:{goal_id}`。`AssessmentGenerator` 以目标和当前画像生成唯一前测，并一次性输出题干、选项、隐藏答案、解析和能力标签；`AssessmentEvaluator` 在 Web 侧按已保存答案确定性评分。用户查看评分、答案与解析后，只有点击“生成学习计划”才创建 `PlanPlanner` AgentRun。`PlanPlanner` 读取目标快照、画像快照和结构化前测交接摘要，输出四阶段路线、节点简要描述和依赖；`PlanValidator` 校验后持久化。
2. **节点教学 Agent（Node Tutor）**：逻辑会话键为 `node_tutor:{plan_node_id}`。`CardContentGenerator` 以目标摘要、节点自然语言简要描述和最新画像生成一份唯一内容与本地 Demo，同时输出内部 `teaching_memory`（关键概念、调用顺序、易错点和可测目标）。内容成功保存后不提供重生入口。用户标记节点完成后，`PostAssessmentGenerator` 只读取该固定内容、Demo 与 `teaching_memory` 生成 5–10 道单选后测，并一次性保存隐藏答案和解析；每次“重新生成后测”创建一份新题集，不改写旧题集或作答。
3. **共享边界**：`PersistAndPublish` 通过 ACL 调用 Core API 持久化结构化结果并发布事件；学习路线、题目判分和授权规则不埋在 prompt 中。评分完全由服务端执行，不调用 LLM。

两类会话都只重建完成当前任务所需的结构化输入快照，不保存或回灌无限原始对话、完整 prompt 或模型原文。这样既保持“同一目标/节点”的上下文连续，也避免不同目标和节点互相污染或撑爆上下文。

### 4.2 可靠性约束

- 每次运行有 `run_id`、`graph_version`、`prompt_version`、`model`、预算和请求幂等键。
- `agent_role` 由 `run_type` 派生；`learning_architect` 只能读本 Goal 的画像/前测交接快照，`node_tutor` 只能读本 PlanNode 的已保存内容、Demo 与教学记忆。每次运行记录 `AgentExecutionProfile` 版本，但不记录完整提示词或模型原文。
- 每个节点设置超时、最大 token/费用、重试次数和可恢复 checkpoint；重试使用指数退避并区分可重试/不可重试错误。
- 输出先通过 JSON Schema 的运行时校验（迁移期 Agent 侧为 Pydantic，目标为 Zod）和安全策略，再通过 ACL/Core API 进入数据库；模型输出视为不可信输入。
- 所有工具采用 allow-list 和最小权限；副作用（抓取外站、执行代码、发送消息）默认需要策略检查或用户确认。
- 前端看到的是事件流（`run.started`、`node.started`、`node.completed`、`run.failed` 等），不是内部 prompt 或秘密。

### 4.3 模型与成本策略

`ModelGateway` 在 `agent-worker` 内部实现，不单独部署容器。所有生成任务只解析账户默认模型连接，从加密的用户模型连接中取得 OpenAI-compatible Base URL 和 API Key；用户只选择模型，不选择 Agent 参数。开发者在 Worker 的版本化执行配置中分别维护学习规划 Agent 与节点教学 Agent 的 System Prompt、输出 Schema、最大输出 Token、超时、工具 allow-list、最大工具调用数、重试和思考模式；不提供用户或管理员配置页面。目标级和任务级模型覆盖后置到 P1。浏览器只向模型连接设置 API 写入 Key；Outbox、队列消息、AgentRun 输入摘要和日志只保存连接 ID/模型名，不能保存明文 Key。

默认生成链路为 `agent-worker → 用户选择的 OpenAI-compatible API`；Adapter 负责协议、结构化输出、流式响应与追踪。embedding/rerank 始终使用独立的固定 profile，不得因用户选择改变 embedding 模型版本。平台仍对每次运行设置 token、时间、并发和重试上限；用户可见实际模型名与失败原因，但 API Key 不可见。自定义 Base URL 仅允许公网 HTTPS 域名和 443 端口，禁止任何 IP 字面量、本机或局域网地址；Worker 的 `SafeModelEgressClient` 会在每次调用时重新解析并校验全部 DNS 结果、以已校验 IP 作为实际 TCP/CONNECT 目标、保留原域名 SNI/证书校验、拒绝重定向并写入 30 天最小审计记录。生产环境还必须通过受控 egress proxy 与云网络规则限制出网。

## 5. API、前端和实时体验

- 外部 API 采用 REST + OpenAPI；TypeScript 内部调用可以共享生成的客户端。若团队极小，可先用 Next.js Route Handlers，保持领域服务不依赖 React。
- 用户查看已评分前测后，`POST /api/v1/learning-goals/:goalId/plans` 才创建规划并立即返回 `agent_run_id`；`POST /api/v1/plan-nodes/:nodeId/content-runs` 在尚无成功内容时创建唯一内容任务；`POST /api/v1/plan-nodes/:nodeId/post-assessment-runs` 每次创建新的后测题集。`GET /api/v1/agent-runs/:id` 查询快照，`GET /api/v1/agent-runs/:id/events` 使用 SSE 重放和订阅事件。后测历史列表和详情仅向题集所有者展示交卷后的答案与解析。
- 所有写接口带幂等键，统一错误码、request-id 和分页；请求体、URL、文件类型和大小在边界层校验。
- 页面首版只需：注册/登录、画像、目标列表与详情、前测、路线图、节点详情、生成状态、节点后测和本地 Demo。进度条、报告、社区先保留数据扩展点，不提前实现复杂 UI。
- UI 实现建议：Tailwind CSS + 无业务规则的组件库；表单用 React Hook Form + Zod；P0 代码以只读/可复制的代码块展示，不引入浏览器编辑器。路线图首版用可访问的阶段/卡片列表表达依赖，避免先引入复杂画布编辑器。

## 6. 内容获取、RAG 和版权

- 首版以系统内置、人工审核的官方文档/视频链接为主；用户粘贴 URL 或上传 Markdown/PDF 可作为受控 P1 入口，不做任意网页全量爬取和视频转写。抓取器限制协议、端口、重定向次数、响应大小和 MIME，阻断内网/云元数据地址，防止 SSRF。
- 清洗、分块、嵌入、索引是可重跑流水线；每步保存版本和哈希，失败可从上一步恢复。
- 生成内容必须携带来源链接/页码；无法找到来源时明确标记“模型推断”，不得伪造引用。
- 尊重 robots、站点条款和用户删除请求；只存必要摘录和用户拥有/授权的内容，设置保留期限。

## 7. 本地代码 Demo 与 P1 在线执行边界

P0 不运行模型或用户代码，因此不部署 Runner，也不会声称服务端已经验证代码可以运行。P0 只要求模型返回下列可读、可复制的本地 Demo 信息：

- 语言与版本、完整文件清单和入口文件；
- 完整代码和关键中文注释；
- 依赖安装步骤、运行命令与预期输出；
- 调用顺序、结果解释和常见报错排查提示。

P1 如引入在线执行，才必须单独通过安全决策，确认支持语言、依赖策略、隔离方案、资源限额、数据保留与成本模型。届时 Runner 必须与 Web/Agent 隔离，默认无网络、非 root、无宿主机挂载，并完成逃逸与资源耗尽回归测试。

## 8. 部署与环境

### 本地开发

本地 `infra/compose.yaml` 启动 PostgreSQL（含 pgvector）、认证限流 Redis、队列 Redis、MinIO、`web`、`agent-dispatcher` 与 `agent-worker`；迁移期同时存在 Python 的 `agent-api`、`agent-dispatcher` 与 `agent-celery-worker`。模型服务不在 Compose 中运行；通过 `.env.example` / Secret 注入用户凭据加密主密钥、固定 embedding Profile/API Key 与平台预算配置。开发机不需要 GPU、模型缓存卷或本地推理运行时。

Docker 内部服务使用服务名互联，生产仅公开反向代理/`web`；PostgreSQL、Redis、MinIO、Dispatcher 与 Agent Worker 不映射公网端口。模型 API Key 只注入 Agent Worker（迁移期为 `agent-celery-worker`），不得通过 `NEXT_PUBLIC_*`、浏览器、日志或内容产物传递。数据库迁移、种子资料和一键健康检查写入 `Makefile`/`pnpm` scripts 与 Worker 的命令入口，确保新成员可在半小时内跑通。

### 生产 MVP

首版生产使用独立的 `infra/compose.production.yaml` 部署 `web`、`agent-dispatcher` 与 `agent-worker`（迁移期额外包含 Python 的三个进程）；它连接外部 PostgreSQL、认证 Redis、队列 Redis 和 S3/R2，不创建这些基础设施容器。可选托管 Next.js，但 Dispatcher 与 Agent Worker 必须在可控的容器环境；模型 API 经 HTTPS 从 Agent Worker 出网调用，并必须经过受控 egress proxy。首版可用受管 Redis 或单 Redis 加备份。面向数千到数万用户时，Worker 与 Dispatcher 需要多副本跨机器部署，并同步预算数据库连接数、出网代理容量与 Provider 配额。启用 HTTPS、域名、每日备份、日志保留、资源限额和自动重启。CI 在合并前执行 lint、类型检查、单元/契约/E2E、迁移检查和镜像漏洞扫描；CD 使用不可变镜像、滚动发布和可回滚迁移。

### 规模化触发条件

按 [09-全栈TypeScript迁移方案](./09-全栈TypeScript迁移方案.md) 3.2 的分档推进：进入增长期（1 万–5 万注册用户，峰值并发 100）前必须具备 Provider 限流与数据库连接预算；进入目标规模（5 万–10 万注册用户，峰值并发 150）前必须完成多机部署、出网代理容量验证与事件表留存策略；若注册用户超过 10 万（峰值 150–300），必须先按 3.1 重算容量模型再扩容。此外出现以下任一情况也应拆分或引入编排平台：队列等待超过 SLO、向量检索延迟明显上升、P1 在线 Sandbox 需要独立节点、数据库连接数接近 `max_connections` 预算、或团队已有专职运维。不要为了“微服务完整”提前引入服务网格、事件总线和独立向量数据库。

## 9. 观测、评测与运维

- 日志：JSON 结构化，包含 `request_id`、`user_id`（哈希）、`run_id`、`node`、`graph_version`、耗时和错误分类；默认不记录完整 prompt、答案和代码。
- 指标：HTTP p50/p95、队列深度/等待、每节点成功率和重试率、模型 API 的延迟/超时/限流/错误率、token/费用、RAG 召回@k/引用覆盖率、本地 Demo schema 完整率、数据库连接池和存储使用量。
- 链路：OpenTelemetry 从浏览器请求贯穿 BFF→Core API/HTTP 或队列→Agent Worker→模型/数据库；Sentry 收集异常并关联 trace。
- Agent 评测：固定 golden set，评估路线结构有效性、前置关系、题目可判分性、引用正确性和本地 Demo 的完整性；prompt/图/模型变更必须可比较、可回滚。
- 运维：健康检查分为 liveness/readiness；配置和 prompt 版本化；定义初步 SLO（例如运行最终成功率、P95 完成时长、错误恢复时间）并在真实数据后调整。

## 10. 安全与隐私基线

- P0 邮箱密码会话使用安全 Cookie、CSRF 防护、Argon2id 密码哈希和 Session 撤销；每个资源执行服务端 owner/tenant 授权，不能只靠前端隐藏按钮。OAuth 回调白名单在 P1 接入 OAuth 时启用。
- API 限流、并发和每日 token/费用配额按用户/IP 生效；上传和抓取限制大小、类型和超时。
- 用户 API Key 只经 HTTPS 写入服务端，以 AES-256-GCM 密文、随机 IV、认证标签和密钥版本存储；不进浏览器响应、日志、源码、Outbox、队列消息或内容产物。`CREDENTIAL_ENCRYPTION_KEY` 仅由 Web 与 Worker 的 Secret/环境变量持有，并须支持轮换。
- 用户可以提交 OpenAI-compatible API Key、模型名和自定义 Base URL；服务端强制超时、并发、token 与重试上限。自定义地址已由 Web 静态校验与 Worker 运行时受控出网双重保护：禁止内网/环回/云元数据地址与所有 IP 字面量，复核 DNS、固定实际连接 IP，限制 HTTPS/443、重定向和响应体，并通过专用 egress proxy 出网。后续新增 Provider 协议或抓取工具时必须复用同一策略，不得直接使用通用 HTTP 客户端。
- 抵御 Prompt Injection：外部资料与系统指令分层、工具权限最小化、引用与内容发布前做策略校验，模型不能自行提升权限或读取任意 URL。
- 加密传输和备份；数据库敏感字段按需要加密/脱敏。提供导出、删除和数据保留策略，删除时同时清理对象存储、向量和运行日志。
- 依赖锁定和定期扫描（npm audit/OSV 等）；生产镜像最小化、非 root、只读文件系统优先。

## 11. MVP 明确取舍

### 必须做

1. 账户与学习者画像（目标、基础、时间、偏好）。
2. 一次前测；评分后显示答案和解析，由用户决定是否生成结构化学习路线图。
3. 用户可任选路线节点生成且只生成一次带引用的学习内容；实战/调试节点生成包含调用顺序、中文注释和本地运行步骤的唯一 Demo。
4. 前测为用户选择的 10–20 道单选题；节点后测为用户选择的 5–10 道单选题且可重新生成新的题集练习；均由服务端根据首次生成时保存的隐藏答案确定性评分，并在交卷后展示答案和解析。
5. 用户标记节点完成后可发起节点后测；不提供在线代码执行、浏览器编辑器或运行日志。
6. 运行状态、错误、重试和重新开始；数据可删除。

### 首版不做

社区/社群、关注和评论；复杂进度条、成就、学习报告；多租户组织、计费；实时协作；在线代码执行、浏览器编辑器、任意语言/任意依赖的代码执行；多 Agent 自主协商、无限原始对话记忆和自动发布到外部系统。

| 风险 | 影响 | MVP 缓解/决策门 |
| --- | --- | --- |
| LLM 生成路线或答案不可靠 | 用户失去信任 | 结构化 schema、引用、质量门、golden set；无法达到引用正确率/代码通过率阈值则限制自动发布。 |
| Agent 长任务超时、重复扣费 | 成本和体验失控 | 队列化、checkpoint、幂等键、预算和超时；所有重试记录 provider 响应。 |
| Prompt injection/恶意网页 | 越权、数据泄露 | SSRF 防护、内容隔离、工具 allow-list、敏感字段脱敏；高风险工具需人工确认。 |
| 本地 Demo 与真实环境不一致 | 用户运行失败、信任下降 | 明确标示 Demo 仅供本地运行；完整输出运行环境、依赖、命令与常见错误；用固定 golden prompt 回归检查结构完整性。 |
| pgvector 数据量和召回质量增长 | 延迟、结果不准 | metadata 过滤、混合检索、HNSW 压测和离线评测；超过容量阈值再迁移。 |
| Next.js/Serverless 请求时限 | 生成任务中断 | HTTP 只创建任务，Worker 执行；SSE 仅订阅事件。 |
| 托管模型 API 限流、故障或成本波动 | 推理不可用、延迟/费用失控 | 每个 profile 设置超时、并发、token/金额上限与可审计 fallback；监控 Provider 错误率、限流和单次运行成本。 |
| 多语言栈维护成本 | 交付变慢、契约漂移 | 已通过 2026-09-16 决策消除：Agent 侧迁移到 TypeScript，最终只保留单一运行时、单一 CI 与单份契约类型。迁移期必须严格按 `run_type` 路由，禁止两套实现长期并存。 |
| 版权和隐私投诉 | 合规/声誉风险 | 存储授权内容与来源、删除机制、保留期限和审计日志；上线前确认目标地区要求。 |

### 建议的验收门槛（可在真实用户前调整）

- 一次学习运行在预算内完成率 ≥ 90%，失败可重试且不产生重复领域对象。
- 路线和节点输出 100% 通过 schema；每个发布段落均有来源或明确的推断标记。
- 题目可判分率 ≥ 95%（单选题选项、隐藏答案和题量均通过结构化校验）；实战/调试 Demo 的语言、入口、代码、运行步骤、预期输出、调用顺序和中文注释均通过结构化校验。
- 未授权用户无法读取他人路线、资料、checkpoint、代码和日志；P0 不存在服务端代码执行入口。
- 关键 API 与 Worker 具备 request/run trace，线上故障可定位到节点、模型和版本。

## 13. 演进路线

1. **MVP（P0）**：单体 Web/BFF + 一个 Agent Worker（内部含学习规划 Agent、节点教学 Agent 两个工作流；迁移期仍为 Python，目标为 TypeScript）+ 托管模型 API + PostgreSQL/pgvector + Redis（迁移期 Celery，目标 BullMQ）；先跑通“画像→前测→评分解析→用户确认规划→任选节点唯一内容与本地 Demo→节点后测历史练习”。低并发时 Agent 可由内部 HTTP 触发，接口仍保持异步契约。
2. **验证期（P1）**：加入在线 Sandbox、浏览器编辑器、检索评测、提示词/图版本管理、缓存、动态路线调整和基础进度事件；根据成本和质量数据决定模型及索引。
3. **增长期**：拆分 ingestion/Sandbox、引入更强隔离和队列伸缩，完善报告、社区、组织权限；只有 pgvector 压测不达标时才评估专用向量库。若 GPU 基础设施、调用量和成本评估同时成立，再将 vLLM 作为自托管推理运行时引入。
