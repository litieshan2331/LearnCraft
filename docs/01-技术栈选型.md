# LearnCraft 技术栈选型（MVP v0.1，A 方案 + 托管模型 API 已确认）

> 面向程序员的个性化学习 Agent：根据用户背景和目标生成学习路线，按路线节点生成可追溯的资料、练习和可运行 Demo（含调用顺序与注释结果）。本文只覆盖可上线的第一个版本，社区、复杂进度体系和学习报告暂不纳入。

## 1. 结论先行

已确认采用 **A 方案：Next.js UI/BFF + Python FastAPI/LangGraph Agent Worker** 的模块化单体架构。Next.js 持有身份、学习画像、规划、内容、测评和实践等核心业务聚合；Python Agent 只负责编排、模型调用、RAG 与受控工具，通过版本化 OpenAPI/JSON Schema 与核心服务通信。这样既保留 Next.js 的全栈开发效率，也为 MinerU 等 Python 文档解析工具、评测和后续资料处理能力预留清晰边界。

本决策基于 LearnCraft 的核心差异化是“资料提取与个性化学习工作流”，而不仅是一个聊天式路线生成器。Python 并非天然让 Agent 更快；它的价值在于更适合承接文档解析、OCR、RAG、评测和数据处理生态。性能瓶颈仍应通过队列、缓存、检索评测、模型预算和独立 Runner 来治理。

| 层次 | 推荐技术 | 选择理由 |
| --- | --- | --- |
| Web/UI/BFF | Next.js App Router、React、TypeScript | 页面、鉴权、API、SSE 流式响应在一个应用内，减少前后端协作成本；未来可单独拆 API。 |
| Agent 编排 | Python FastAPI + LangGraph + LangChain | Python 侧的解析、检索、评测和沙箱生态更完整；LangGraph 用有状态图表达“前测→规划→检索→生成→校验”的可恢复工作流，LangChain 负责模型、检索器和工具适配。FastAPI 只暴露薄的内部运行入口。 |
| 模型接入 | 应用内 `ModelGateway`（LangChain provider integrations + 托管模型 API 适配器） | `ModelGateway` 是代码内门面，不是额外容器；按任务角色、预算和能力白名单选择模型 profile，不把具体模型名、base URL 或密钥写进领域代码。 |
| 模型运行时 | 已批准的托管生成/embedding API | `agent-worker` 直接调用托管 API，不运行本地模型或 GPU 推理服务；生成、embedding、rerank 可使用独立且版本固定的 profile。 |
| 异步与限流 | PostgreSQL Outbox + Dispatcher + Celery；认证 Redis 与 Celery Redis 分离 | 长任务统一返回 `202 + agentRunId`，不阻塞 Web 请求。Dispatcher 可靠投递 Outbox，Celery 执行可重试任务；两个 Redis 均固定 DB 0，但物理实例、密码和键前缀独立。未来各自可迁托管 Redis/Sentinel。 |
| 业务数据 | PostgreSQL 16+ | 事务、JSONB、全文检索和生态成熟；用户、路线、题目、运行记录都放在同一事实源。 |
| 向量检索 | `VectorStore` 抽象 + P0 `PgvectorVectorStore` | P0 用 pgvector，让事务数据和向量 metadata 可一起过滤；业务代码不直接依赖 pgvector SQL。数据规模、吞吐或压测证明需要时，再以 `MilvusVectorStore` 替换适配器，而不是重写工作流。 |
| ORM/迁移 | Web 侧 Drizzle ORM + drizzle-kit；Agent 侧仅用 SQLAlchemy/asyncpg 访问编排基础设施表 | TypeScript 业务 schema 类型安全、SQL 透明；Python Agent 不共享 Web ORM Model，只能经 Core API 写业务聚合，必要时通过独立 checkpoint repository 访问自己的表。迁移文件纳入版本库。 |
| 校验/契约 | OpenAPI/JSON Schema；Web 用 Zod，Agent 用 Pydantic | 跨语言请求、响应、领域事件和 LLM 结构化输出均有版本化契约；生成 TypeScript/Python 客户端，避免手写漂移。 |
| 文件/原始资料 | S3 兼容对象存储（本地 MinIO，生产 S3/R2） | PDF、网页快照、代码产物不塞进数据库；数据库只保存 URI、哈希和元数据。 |
| 代码执行 | 独立 Runner 容器（Docker，默认无网络） | 与 Web/Agent 进程隔离，限制 CPU、内存、磁盘和执行时长；生产再替换为 gVisor/Firecracker/托管 Sandbox。 |
| 鉴权 | P0 邮箱密码（Argon2id）+ 不透明数据库 Session/HttpOnly Cookie + 服务端授权策略 | 先完成可本地联调的注册、登录、资源归属校验和会话管理；OAuth/Magic Link、找回密码和复杂 RBAC 放 P1。 |
| 测试 | Vitest、pytest、Playwright、Testcontainers、Graph fixture/eval | 覆盖领域规则、跨语言契约、关键用户流程和 Agent 回归样例。 |
| 可观测性 | OpenTelemetry、结构化日志、Sentry；可选 LangSmith | 跟踪一次学习运行跨 API、队列、图节点和模型调用的完整链路；敏感内容默认脱敏。 |
| 部署 | Docker Compose（本地）→ 单台云主机/容器平台（生产 MVP） | 本地 Compose 启动全部依赖；生产 Compose 只启动 Web、Agent API、Dispatcher 与 Celery Worker，连接外部 PostgreSQL、Redis 和对象存储。 |

### 托管模型 API 采用前提

MVP 不在本地或 Docker 中运行大模型，因此不需要 GPU、模型权重缓存、显存预算或推理服务运维。代价是需要管理 Provider 的 API key、额度、超时、限流、重试、费用与降级策略；这些都由 `agent-worker` 内的 ModelGateway 统一处理。未来有稳定 GPU 基础设施、持续并发和明确成本收益后，才重新评估加入 vLLM；当前不把它放入实现或 Compose 范围。

### P0 已锁定的 Embedding Profile

| 配置项 | 固定值 |
| --- | --- |
| Provider | `SiliconFlow` |
| Model | `BAAI/bge-m3` |
| Dimension | `1024` |
| Metric | `cosine` |
| Profile Version | `siliconflow-bge-m3-v1` |

该 profile 只用于 embedding；生成模型仍由后续 `ModelGateway` 选型决定。`SILICONFLOW_API_KEY` 只放在 `infra/.env` 或生产 Secret Manager，绝不提交。创建 `content_chunks.embedding vector(1024)` 迁移后，不能原地修改这些值；升级模型必须新建 profile 并完成重嵌入。

### 为什么确认 Python Agent 边界

这里不是把业务后端拆成两套，而是把高变化、长耗时的 Agent 编排隔离出来。Python 侧承接 LangGraph、LangChain、MinerU/文档解析适配器、评测、数据处理和沙箱相关能力；LangGraph 的 checkpoint、节点回放和图测试也集中在一个 Worker。Next.js 仍是用户唯一入口，核心领域规则只在 `apps/web/src/modules/*` 实现一次。跨语言只共享 `packages/contracts` 的 OpenAPI/JSON Schema 与事件信封，不共享 ORM Model 或领域类。

该边界的代价是需要维护 Node 与 Python 的 CI、运行时和契约生成，因此必须坚持以下约束：

- Agent 只能通过 Core API/ACL 和明确的 ports 读取或改变学习业务；不能直接改 `learning_plans`、`assessments` 等核心表。
- 所有 Agent 命令异步化，使用 `agent_run_id`、幂等键、graph/prompt 版本和可恢复 checkpoint；Core API 负责授权、事务和状态机。
- OpenAPI/JSON Schema 在 CI 中做破坏性变更检查，并同时生成 TypeScript 与 Pydantic 类型。
- Python Worker 内部再按 `workflows`、`tools`、`infrastructure` 分层；MinerU 等解析器只能作为可替换适配器，不能把其数据模型泄漏到 Learning Content 领域层。

当前 MVP 不在 Next.js 内重写 Agent 工作流，也不采用 LangGraph.js 作为第二套实现。若未来确认不再需要 Python 资料处理能力，才可重新评估 B 方案；届时必须保持 Core API/AgentRun 契约稳定，而不是并行维护两套图逻辑。

### 方案选择记录（A 已确认）

| 方案 | 优点 | 代价 | 适用判断 |
| --- | --- | --- | --- |
| **A. Next.js BFF + Python Agent Worker（已确认）** | 保留 Next.js 全栈开发体验；Python 的解析、RAG、MinerU 集成、评测和沙箱生态更适合本产品；长流程可独立扩缩 | 两套运行时，需要 OpenAPI/JSON Schema、ACL 和双 CI | **LearnCraft MVP 的实施方案** |
| B. Next.js + LangGraph.js 单语言 | 共享 TypeScript 类型，部署和本地调试最简单 | 资料解析、RAG 评测等 Python 工具通常仍需额外服务 | 不纳入当前 MVP；仅在不再需要 Python 资料处理能力时重评估 |
| C. Next.js + 独立 Python Core API + Python Agent | 领域层与 Agent 都在 Python，边界清晰 | 前端、Core API、Agent 三个进程；首版运维和契约成本最高 | 不纳入当前 MVP |

无论选择哪一行，**领域模型只保留一份、Agent 通过 AgentRun 异步执行、代码 Runner 独立隔离**这三条不变。

本文所说的 `Core API` 在 MVP 中就是 Next.js 的 Route Handler/BFF 加 `src/modules/*` 应用服务，不另起一个 Node API 进程；当接口规模或团队边界需要时，再按 DDD 文档的迁移路线抽成独立服务。

## 2. 总体部署拓扑

```text
Browser
   │ HTTPS
   ▼
Next.js Web/BFF ──Core API/ACL──► Python FastAPI Agent API（健康检查 / 内部接口）
   │
   │ 业务事务/授权
   ▼
PostgreSQL + pgvector（P0）
   │
   └── AgentRun + Outbox ──► agent-dispatcher ──► Celery Redis ──► agent-celery-worker
                                                                    │
                                                                    ├── LangGraph + ModelGateway
                                                                    ├── 托管 LLM / Embedding API
                                                                    ├── Content Fetch/Parse（白名单、SSRF 防护）
                                                                    └── Code Runner（Python 3.11、短生命周期、无网络容器）

S3-compatible Object Storage ◄── 原始资料、运行产物
OpenTelemetry/Sentry ─────────── Web、Agent、Runner 的日志、指标和追踪
```

### 进程职责

- `web`：渲染界面、会话、资源授权、核心领域 command/query、创建 `AgentRun`、通过 SSE 推送运行事件。不得在请求线程执行长时间 LLM 调用或用户代码。
- `agent-api`：保留的 Python FastAPI 进程，当前提供仅内网的健康检查，后续承接受服务身份保护的内部接口。
- `agent-dispatcher`：使用 `FOR UPDATE SKIP LOCKED` 领取 `agent.run.requested` Outbox 事件，投递后回写 `published`；若在发送后中断允许重复投递。
- `agent-celery-worker`：消费 `agent.run`，以 `agent_run_id` 作为 Celery `task_id`，维护 AgentRun 生命周期、协作式取消检查、超时和重试；后续执行 LangGraph 并经 Core API/ACL 请求领域写入。
- `model-provider`：外部托管模型 API，不是 Compose 服务；只有 `agent-worker` 持有对应 API key 并负责超时、预算、重试和可审计 fallback。
- `code-runner`：仅接收已校验的代码和运行配置，使用一次性工作目录执行，返回 stdout/stderr/退出码/资源用量；Runner 无权访问主数据库凭据。
- `ingestion`：首版可作为 Agent Worker 内的受限模块，负责受控 URL/PDF/Markdown 获取、清洗、切块和嵌入；MinerU 等解析能力以 adapter 方式接入，并通过 Content 的 application port/API 写入；数据量上升后拆成独立 Worker。

Web 与 Agent 之间使用内部服务身份（短期 token/mTLS 或 HMAC），Agent 端点不暴露公网；Core API 负责用户授权和领域事务，Agent 不能以“工具调用”绕过这些检查。

## 3. 向量检索存储设计（P0 为 PostgreSQL + pgvector）

### 3.1 数据分工

PostgreSQL 是业务事实源，建议至少包含以下表（实际字段以领域模型为准）：

`users`、`learner_profiles`、`learning_goals`、`learning_plans`、`plan_nodes`、`content_sources`、`content_documents`、`content_chunks`、`quiz_items`、`quiz_attempts`、`code_runs`、`agent_runs`、`agent_checkpoints`、`outbox_events`。产品界面可把 `agent_runs` 展示为“学习运行”，但数据库和契约统一使用 `agent_run_id`。

- 领域状态使用明确列；模型原始响应、图状态和可演进元数据放入受控 `jsonb`，并记录 schema/version。
- 所有用户归属资源带 `owner_id`（未来多租户可增加 `tenant_id`），服务层每次查询都执行授权过滤；高隔离部署再启用 PostgreSQL RLS。
- 状态迁移通过事务完成；跨服务副作用写入 `outbox_events`，由 Dispatcher 投递到 Celery，避免“数据库已提交但任务未发送”。
- 原始网页/PDF放对象存储，表中保存 `source_uri`、内容哈希、抓取时间、解析器版本和版权/可见性信息。

### 3.2 向量检索约定

- Agent 的检索工作流只依赖 `application.ports.VectorStore`：`upsert`、`delete`、`search`。它可承载 dense 与 sparse 两类向量；单次 `search` 只查询一种模态，统一以“`score` 越高越相关”表示命中，不泄漏 pgvector 的 `<=>` 距离表达式、Milvus collection 或 SDK 类型。
- P0 仅实现 `PgvectorVectorStore`。未来 Milvus 仅作为 `MilvusVectorStore` 的替代适配器，不与 pgvector 双写，也不让领域模型直接依赖任一数据库。
- `content_chunks.embedding` 使用 `vector(n)`；`n` 由 embedding provider 配置决定，切换模型必须新建版本或重嵌入，不能混用维度。
- P0 先使用余弦距离精确检索；在数据量较小或频繁写入阶段不建 ANN 索引。达到检索 p95/内容量阈值并通过离线评测后，再建立 HNSW；索引参数（`m`、`ef_construction`、查询 `ef_search`）通过迁移和配置固定并压测。
- 查询先按 `owner_id`、来源类型、语言、技术栈、版本等 metadata 过滤，再做向量召回；P0 使用 dense 向量召回与 PostgreSQL FTS（`tsvector`）分别产出候选集，再由 `HybridRetriever` 以 RRF 融合排序，避免只靠语义相似度。FTS 是词法检索，不等同于 BGE-M3 的学习型 sparse embedding，但足以补足托管 Embedding API 仅返回 dense 向量的限制。
- 若未来接入能返回 sparse 向量的模型，`VectorStore` 可写入并单独检索 `SparseVector`；上层仍分别取得 dense、sparse、FTS 的排序列表后融合。ColBERT 多向量/MaxSim 是另一种检索表示，届时应新增专用端口或 reranker，而不是伪装为一个 sparse 向量。
- Agent 的 RAG 查询必须经 Content context 的 `RetrieverPort`/Core API（带用户归属和来源授权过滤），不得直接把 pgvector 表暴露给图节点或 UI；返回结果必须包含 `document_id`、`chunk_id` 和来源定位，供引用校验。
- 每个 chunk 保存 `embedding_model`、`embedding_version`、`chunker_version`、`token_count` 和来源定位（URL/页码/行号），生成内容必须返回可点击引用。
- 建立离线检索评测集（问题、期望来源、召回@k、引用正确率），不要以“主观感觉”决定索引或模型。

### 3.3 未来迁移 Milvus 的约束

Milvus 的价值主要在于大规模向量、并发索引和检索吞吐的扩展能力；它不会自动修复 embedding、分块、查询改写、metadata 过滤或重排序造成的低召回。pgvector 同样支持精确检索、HNSW 与 PostgreSQL 全文检索，P0 应先用离线评测定位质量问题。[pgvector 官方说明](https://github.com/pgvector/pgvector)

当压测证实 pgvector 已无法满足已确认的规模或延迟目标时，再向用户提交 Milvus 迁移方案：collection/metadata 映射、全量 backfill、离线 recall@k 与引用正确率对比、灰度双读、切换开关、成本估算和回滚步骤。Milvus 支持 ANN、metadata filtering、全文/混合检索与水平扩展，但这些能力须通过适配器和评测引入。[Milvus 官方概览](https://milvus.io/docs/overview.md)

### 3.4 连接、备份和迁移

- Web/Agent 使用各自的连接池；长任务不能占用 Core API 事务连接等待模型响应。Agent 直接连接数据库时只允许 checkpoint/运行事件等基础设施 repository，业务聚合必须经 Core API。
- 生产启用自动备份、PITR、恢复演练和迁移前快照；开发环境用 Testcontainers/Compose 重建，不依赖手工改表。
- pgvector 版本、PostgreSQL 版本和 embedding 维度写入 `system_settings`/迁移元数据，并在启动健康检查中校验。

## 4. Agent 编排方案

### 4.1 图状态与节点

LangGraph State 建议采用可版本化的 `AgentRunState`（只放可序列化数据），节点命名与 PRD/契约保持一致：

1. `InputNormalizer`：校验目标、画像、偏好和主题边界，形成规范化输入。
2. `AssessmentSelector/Generator`：从受控题库选择或生成 5–8 道选择题 + 简答题（前测/随堂共用题型合同），输出固定 schema 和隐藏 rubric。
3. `AssessmentEvaluator`：选择题规则判分；简答题用固定结构化输出 Profile 按 rubric 返回分数、能力标签和置信度，并经 Core API 保存评估结果；低置信度不触发路线调整。
4. `PlanPlanner`：生成概念→语法→实战→调试四阶段路线、卡片和依赖。
5. `PlanValidator`：校验数量、阶段覆盖、前置无环、时长和主题边界；失败只回退规划节点。
6. `CardContentGenerator`：按卡片和偏好检索已授权资料，生成解释、练习、代码和引用；实战/调试节点输出可运行 Demo、调用顺序和注释结果，并先经 Runner 验证。
7. `QuizGenerator/Evaluator`：生成并评分卡后测，题量/题型与前测一致（5–8 道选择题 + 简答题），绑定学习目标。
8. `AdaptationPolicy`：使用显式规则决定解锁、复习或插入补强卡；模型只能提供候选理由/标签。
9. `PersistAndPublish`：通过 ACL 调用 Core API 的应用服务，提交结构化结果并发布事件；不能直接写学习领域聚合。

图层只负责编排、重试、超时、人工确认和工具调用；学习路线、题目判分等业务不直接埋在 prompt 中，应由领域服务和应用服务实现。

### 4.2 可靠性约束

- 每次运行有 `run_id`、`graph_version`、`prompt_version`、`model`、预算和请求幂等键。
- 每个节点设置超时、最大 token/费用、重试次数和可恢复 checkpoint；重试使用指数退避并区分可重试/不可重试错误。
- 输出先通过 Pydantic/JSON Schema（Web 边界再用 Zod）和安全策略，再通过 ACL/Core API 进入数据库；模型输出视为不可信输入。
- 所有工具采用 allow-list 和最小权限；副作用（抓取外站、执行代码、发送消息）默认需要策略检查或用户确认。
- 前端看到的是事件流（`run.started`、`node.started`、`node.completed`、`run.failed` 等），不是内部 prompt 或秘密。

### 4.3 模型与成本策略

`ModelGateway` 在 `agent-worker` 内部实现，不单独部署容器。它把 `task_role`（规划、内容、测验、embedding）、`generation_mode` 与预算映射到服务端白名单 `ModelProfile`；每个 profile 记录 provider/model、能力、超时、token 上限、价格快照和 fallback 链。前端与领域层不能传任意 model、base URL、provider 参数或 API key。

默认生成链路为 `agent-worker → 托管模型 API`；LangChain Provider Adapter 负责协议、结构化输出、流式响应与追踪。embedding/rerank 可先使用独立的固定 profile；不得因用户选择或一次运行中的隐式切换而改变 embedding 模型版本。为每次运行设置 token、时间、金额、并发和重试上限；记录 requested/actual profile、模型版本、fallback 原因、输入/输出 token 与估算费用。fallback 只允许能力兼容的白名单模型，且必须可观测，不能静默切换。

## 5. API、前端和实时体验

- 外部 API 采用 REST + OpenAPI；TypeScript 内部调用可以共享生成的客户端。若团队极小，可先用 Next.js Route Handlers，保持领域服务不依赖 React。
- `POST /api/v1/plans` 创建规划并立即返回 `agent_run_id`；`GET /api/v1/agent-runs/:id` 查询快照；`GET /api/v1/agent-runs/:id/events` 使用 SSE 重放和订阅事件。断线后按 `Last-Event-ID` 补发，不能只依赖内存；“学习运行”只是 UI 文案。
- 所有写接口带幂等键，统一错误码、request-id 和分页；请求体、URL、文件类型和大小在边界层校验。
- 页面首版只需：注册/登录、目标采集、路线图、节点详情、生成状态、题目作答和 Demo 运行结果。进度条、报告、社区先保留数据扩展点，不提前实现复杂 UI。
- UI 实现建议：Tailwind CSS + 无业务规则的组件库；表单用 React Hook Form + Zod；代码编辑器先选 CodeMirror 6（若需要更重的 IDE 能力再换 Monaco）。路线图首版用可访问的阶段/卡片列表表达依赖，避免先引入复杂画布编辑器。

## 6. 内容获取、RAG 和版权

- 首版以系统内置、人工审核的官方文档/视频链接为主；用户粘贴 URL 或上传 Markdown/PDF 可作为受控 P1 入口，不做任意网页全量爬取和视频转写。抓取器限制协议、端口、重定向次数、响应大小和 MIME，阻断内网/云元数据地址，防止 SSRF。
- 清洗、分块、嵌入、索引是可重跑流水线；每步保存版本和哈希，失败可从上一步恢复。
- 生成内容必须携带来源链接/页码；无法找到来源时明确标记“模型推断”，不得伪造引用。
- 尊重 robots、站点条款和用户删除请求；只存必要摘录和用户拥有/授权的内容，设置保留期限。

## 7. 在线代码 Demo 的安全边界

这是最高风险组件，必须与 Agent/Web 隔离：

- Runner 使用非 root、一次性容器/沙箱，默认断网、只读基础镜像、临时工作目录、禁止宿主机挂载和设备访问。
- 强制 CPU、内存、进程数、磁盘、输出字节和 wall-clock 限额；超限立即杀进程并回收容器。
- 语言和依赖采用 allow-list；MVP 只开放 Python 3.11 及预置依赖，不支持任意 `pip install`/`npm install`。
- 代码、日志和生成文件先做大小及敏感信息过滤；Runner 返回结构化结果，不返回宿主机路径或凭据。
- 生产上线前完成恶意代码、逃逸、资源耗尽和供应链测试；若无法满足隔离，宁可先提供静态代码/远程演示，不开放执行。

## 8. 部署与环境

### 本地开发

本地 `infra/compose.yaml` 启动 PostgreSQL（含 pgvector）、认证限流 Redis、Celery Redis、MinIO、`web`、`agent-api`、`agent-dispatcher` 和 `agent-celery-worker`。模型服务不在 Compose 中运行；通过 `.env.example` / Secret 注入已批准 Provider 的 API key、模型 profile 与预算配置。开发机不需要 GPU、模型缓存卷或本地推理运行时。

Docker 内部服务使用服务名互联，生产仅公开反向代理/`web`；PostgreSQL、Redis、MinIO、`agent-api`、Dispatcher、Celery Worker 和 Runner 不映射公网端口。模型 API key 只注入 `agent-celery-worker`，不得通过 `NEXT_PUBLIC_*`、浏览器、日志或 Runner 传递。数据库迁移、种子资料和一键健康检查写入 `Makefile`/`pnpm` scripts 与 Agent 的 `uv`/`pytest` 命令，确保新成员可在半小时内跑通。

### 生产 MVP

首版生产使用独立的 `infra/compose.production.yaml` 部署 `web`、`agent-api`、`agent-dispatcher` 与 `agent-celery-worker`；它连接外部 PostgreSQL、认证 Redis、Celery Redis 和 S3/R2，不创建这些基础设施容器。可选托管 Next.js，但 Dispatcher、Celery Worker 与 Runner 必须在可控的容器环境；模型 API 经 HTTPS 从 Celery Worker 出网调用。首版可用受管 Redis 或单 Redis 加备份，后续通过环境变量切换 Celery Redis Sentinel。启用 HTTPS、域名、每日备份、日志保留、资源限额和自动重启。CI 在合并前执行 lint、类型检查、单元/契约/E2E、迁移检查和镜像漏洞扫描；CD 使用不可变镜像、滚动发布和可回滚迁移。

### 规模化触发条件

达到以下任一条件再拆服务或上 Kubernetes：并发运行数持续超过单 Worker 容量、队列等待超过 SLO、向量检索延迟明显上升、Runner 需要独立节点、或团队已有专职运维。不要为了“微服务完整”提前引入服务网格、事件总线和独立向量数据库。

## 9. 观测、评测与运维

- 日志：JSON 结构化，包含 `request_id`、`user_id`（哈希）、`run_id`、`node`、`graph_version`、耗时和错误分类；默认不记录完整 prompt、答案和代码。
- 指标：HTTP p50/p95、队列深度/等待、每节点成功率和重试率、模型 API 的延迟/超时/限流/错误率、token/费用、RAG 召回@k/引用覆盖率、代码运行超时率、数据库连接池和存储使用量。
- 链路：OpenTelemetry 从浏览器请求贯穿 BFF→Core API/HTTP 或队列→Python Worker→模型/数据库/Runner；Sentry 收集异常并关联 trace。
- Agent 评测：固定 golden set，评估路线结构有效性、前置关系、题目可判分性、引用正确性和代码可运行率；prompt/图/模型变更必须可比较、可回滚。
- 运维：健康检查分为 liveness/readiness；配置和 prompt 版本化；定义初步 SLO（例如运行最终成功率、P95 完成时长、错误恢复时间）并在真实数据后调整。

## 10. 安全与隐私基线

- P0 邮箱密码会话使用安全 Cookie、CSRF 防护、Argon2id 密码哈希和 Session 撤销；每个资源执行服务端 owner/tenant 授权，不能只靠前端隐藏按钮。OAuth 回调白名单在 P1 接入 OAuth 时启用。
- API 限流、并发和每日 token/费用配额按用户/IP 生效；上传和抓取限制大小、类型和超时。
- 模型密钥只存在服务端 Secret Manager/环境变量，不进浏览器、日志、源码或 Runner；密钥按 provider 分离并可轮换。
- 托管模型 API key 按 Provider 与环境分离、可轮换；只由 `agent-worker` 出网调用，设置 API 超时、并发、限流和单次运行预算。用户不得提交自定义 API key、任意 base URL 或 Provider 参数。
- 抵御 Prompt Injection：外部资料与系统指令分层、工具权限最小化、引用/代码执行前做策略校验，模型不能自行提升权限或读取任意 URL。
- 加密传输和备份；数据库敏感字段按需要加密/脱敏。提供导出、删除和数据保留策略，删除时同时清理对象存储、向量和运行日志。
- 依赖锁定和定期扫描（npm audit/OSV 等）；生产镜像最小化、非 root、只读文件系统优先。

## 11. MVP 明确取舍

### 必须做

1. 账户与学习者画像（目标、基础、时间、偏好）。
2. 一次前测并生成结构化学习路线图。
3. 点击路线节点生成带引用的学习内容（概念→语法→实战→调试模板）；实战/调试 Demo 必须预运行验证，展示调用顺序与注释结果。
4. 前测和随堂测验均为 5–8 道选择题 + 简答题；选择题规则判分，简答题 AI rubric 判分。
5. 受限代码 Demo 运行，展示 stdout/stderr/退出码以及与调用顺序对应的注释结果。
6. 运行状态、错误、重试和重新开始；数据可删除。

### 首版不做

社区/社群、关注和评论；复杂进度条、成就、学习报告；多租户组织、计费；实时协作；任意语言/任意依赖的代码执行；多 Agent 自主对话、长期记忆和自动发布到外部系统。

## 12. 主要风险与决策门

| 风险 | 影响 | MVP 缓解/决策门 |
| --- | --- | --- |
| LLM 生成路线或答案不可靠 | 用户失去信任 | 结构化 schema、引用、质量门、golden set；无法达到引用正确率/代码通过率阈值则限制自动发布。 |
| Agent 长任务超时、重复扣费 | 成本和体验失控 | 队列化、checkpoint、幂等键、预算和超时；所有重试记录 provider 响应。 |
| Prompt injection/恶意网页 | 越权、数据泄露 | SSRF 防护、内容隔离、工具 allow-list、敏感字段脱敏；高风险工具需人工确认。 |
| 代码沙箱逃逸 | 严重安全事故 | 默认不开放任意执行；先用托管/强隔离 Sandbox，完成攻击测试后逐步放量。 |
| pgvector 数据量和召回质量增长 | 延迟、结果不准 | metadata 过滤、混合检索、HNSW 压测和离线评测；超过容量阈值再迁移。 |
| Next.js/Serverless 请求时限 | 生成任务中断 | HTTP 只创建任务，Worker 执行；SSE 仅订阅事件。 |
| 托管模型 API 限流、故障或成本波动 | 推理不可用、延迟/费用失控 | 每个 profile 设置超时、并发、token/金额上限与可审计 fallback；监控 Provider 错误率、限流和单次运行成本。 |
| 多语言栈维护成本 | 交付变慢 | Python 只限 Agent 编排与资料处理；核心业务仍是 Next.js/TypeScript，契约生成和统一 CI 防止两套领域模型漂移。MVP 不并行维护 LangGraph.js 实现。 |
| 版权和隐私投诉 | 合规/声誉风险 | 存储授权内容与来源、删除机制、保留期限和审计日志；上线前确认目标地区要求。 |

### 建议的验收门槛（可在真实用户前调整）

- 一次学习运行在预算内完成率 ≥ 90%，失败可重试且不产生重复领域对象。
- 路线和节点输出 100% 通过 schema；每个发布段落均有来源或明确的推断标记。
- 题目可判分率 ≥ 95%（简答题含结构化输出/置信度校验）；实战/调试 Demo 在受支持环境中的预运行通过率 ≥ 90%。
- 未授权用户无法读取他人路线、资料、checkpoint、代码和日志；Runner 无法访问宿主机和内部网络。
- 关键 API 与 Worker 具备 request/run trace，线上故障可定位到节点、模型和版本。

## 13. 演进路线

1. **MVP**：单体 Web/BFF + 一个 Python Agent Worker + 托管模型 API + PostgreSQL/pgvector +（可选）Redis Streams + 受限 Runner；先跑通“画像→前测→路线→节点内容→题目/Demo”。低并发时 Agent 可由内部 HTTP 触发，接口仍保持异步契约。
2. **验证期**：加入检索评测、提示词/图版本管理、缓存、动态路线调整和基础进度事件；根据成本和质量数据决定模型及索引。
3. **增长期**：拆分 ingestion/runner、引入更强隔离和队列伸缩，完善报告、社区、组织权限；只有 pgvector 压测不达标时才评估专用向量库。若 GPU 基础设施、调用量和成本评估同时成立，再将 vLLM 作为自托管推理运行时引入。
