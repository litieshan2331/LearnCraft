# LearnCraft 多模型智能路由与统一网关改造方案

> 对应《10-项目改造以及投递核心技术亮点》中的“亮点一：多模型智能路由与统一网关（Model Router & Gateway）”。
>
> 本文基于 2026-09-23 仓库实际代码整理，只描述当前能力、目标方案和实施边界，不代表相关能力已经全部实现。

## 一、结论

LearnCraft 当前已经具备较好的模型调用安全基础和异步任务基础，包括 OpenAI-compatible 模型调用、上游 SSE 解析、429/5xx 重试、BullMQ 异步队列、任务幂等、Token 用量回写、凭据加密以及受控模型出网。

但是，当前实现还不能称为完整的“多模型智能路由与高并发统一网关”：
- 智能路由尚未实现，Agent 每次只读取账户中处于 active 状态的默认模型连接；
- 只支持 OpenAI-compatible 协议，没有 Anthropic 原生协议适配器；
- 已有请求重试，但没有备用模型降级、模型级熔断、健康检查和负载均衡；
- 没有模型 Provider/账户维度的 RPM、TPM 和并发限制；
- 当前会把上游 SSE 事件完整保存到数组后再聚合，不是真正的低内存下游流式透传；
- Worker 虽然支持配置异步并发，但当前默认并发为 5，尚未完成容量压测，不能声称“单机支撑 1000+ 并发对话”。

因此，更准确的项目表述应当是：**当前已完成安全模型调用网关和分布式异步执行基础，智能路由、统一多协议适配、模型级流控与真实高并发验证仍属于后续改造内容。**

## 三、目标架构

建议新增独立的 TypeScript 模型网关服务，并让 Web、Agent Worker 和后续评测服务统一通过该网关调用模型：

```text
Web / Agent Worker / Evaluation Worker
                 │
                 ▼
        OpenAI-compatible Gateway API
                 │
                 ▼
        鉴权、租户识别与请求校验
                 │
                 ▼
       RPM / TPM / 并发 / 预算准入控制
                 │
                 ▼
        Model Router 生成 RoutePlan
                 │
                 ▼
   Provider Adapter + 重试 / 熔断 / 降级
                 │
                 ▼
          OpenAI / Anthropic 
                 │
                 ▼
 SSE 协议归一化、背压转发、用量结算与观测
```

模型网关应当作为通用基础设施存在，业务工作流只表达“需要什么能力”，不在业务代码中硬编码具体厂商和模型选择条件。

## 四、统一网关接口

首期建议提供与 OpenAI Chat Completions 兼容的接口：

```text
POST /v1/chat/completions
```

网关内部使用统一对象表示：

- system、user、assistant、tool 消息；
- 文本输出、推理增量和工具调用；
- JSON 结构化输出要求；
- 流式事件；
- finish reason；
- 输入、输出和缓存 Token；
- Provider 错误和稳定的网关错误码。

Agent Worker 不再直接依赖某个 Provider 的响应格式，而是依赖网关统一协议。对外接口可以继续保持 OpenAI-compatible，内部再通过 Provider Adapter 完成协议转换。

## 五、Provider Adapter

建议为不同 Provider 定义统一适配接口：

```ts
interface ModelProviderAdapter {
  supports(capability: ModelCapability): boolean;
  stream(request: UnifiedModelRequest): AsyncIterable<UnifiedModelChunk>;
}
```

首批适配范围建议为：

1. OpenAI-compatible：复用当前模型网关和安全出网能力；
2. Anthropic：处理 Messages API、工具调用和流式事件差异。

不建议无条件引入所有厂商 SDK。若 HTTP 协议稳定且现有安全出网客户端可以覆盖，直接实现轻量 HTTP Adapter 更容易统一超时、审计、重试和安全策略。

## 六、智能路由策略

### 6.1 路由输入

路由不应只依赖 Prompt 字符数，应综合以下信息：

- 工作流类型，例如 assessment、plan、card content、posttest；
- 预估输入 Token 和最大输出 Token；
- 是否需要工具调用；
- 是否要求 JSON 或严格结构化输出；
- 是否需要长上下文、视觉输入或强推理能力；
- 用户等级、账户预算和单次调用预算；
- 模型价格、上下文窗口和能力标签；
- 模型最近的 TTFT、总延迟、429 比例和错误率；
- 当前活跃请求数、RPM/TPM 余量及熔断状态；
- 数据合规、地区和 Provider 使用限制。

### 6.2 路由流程

建议采用以下确定性流程：

1. 硬约束过滤：排除不支持工具调用、JSON、上下文长度或合规要求的模型；
2. 准入检查：排除 RPM、TPM、并发、预算不足或已熔断的模型；
3. 加权评分：综合能力、成本、延迟、健康度和当前负载；
4. 生成有序 `RoutePlan`：主模型加若干能力等价的备用模型；
5. 记录路由原因，便于审计、评测和面试展示。

首版建议使用规则和加权评分，不建议额外调用一个 LLM 负责路由。LLM Router 会增加一次模型费用、额外延迟和新的故障点，也难以稳定复现路由决策。

示例路由规则：

```text
短文本 + 无工具 + 普通用户     → 低成本模型
长上下文 + 复杂学习规划        → 长上下文/强推理模型
要求工具调用或严格 JSON        → 具备对应能力的模型集合
主模型 429 或熔断              → 能力等价且预算允许的备用模型
账户预算不足                   → 更低成本模型或明确拒绝
```

## 七、高可用、重试与降级

### 7.1 限流与准入控制

建议使用 Redis Lua 原子实现以下控制：

- 租户/API Key 维度 RPM；
- 租户/API Key 维度 TPM；
- Provider 和模型维度 RPM/TPM；
- 模型级活跃并发信号量；
- 用户日预算和月预算；
- 预估 Token 预占与真实 Token 结算。

Redis 负责实时热状态，PostgreSQL 负责最终用量和费用流水，不能只依赖 Redis 保存计费事实。

### 7.2 重试

可以重试的情况包括：

- 连接超时；
- 读取超时；
- HTTP 429；
- HTTP 5xx；
- Provider 返回可恢复错误。

应使用带抖动的指数退避，并且所有重试共享一次请求的总超时预算，避免网关层重试和 BullMQ 任务重试叠加后造成超长延迟和费用失控。

### 7.3 熔断

按照 `Provider + Endpoint + Model` 维护熔断状态：

```text
Closed → 连续失败达到阈值 → Open
Open   → 冷却时间结束     → Half-Open
Half-Open → 探测成功      → Closed
Half-Open → 探测失败      → Open
```

健康度不能只依赖主动探活，还应结合真实请求的错误率、429 比例、TTFT 和总延迟。

### 7.4 降级边界

只有满足下列条件才允许自动降级：

- 备用模型具备当前请求要求的工具、JSON、上下文和推理能力；
- 数据合规和 Provider 使用范围一致；
- 备用模型费用没有突破预算；
- 尚未向下游发送不可撤回的正文数据。

流式请求一旦已经向客户端发送首个正文 Token，就不能透明切换到另一模型，否则可能造成前后语义不一致或重复输出。此时应结束流并返回稳定错误，而不是拼接两个模型的答案。

## 八、真正的 SSE 流式转发

当前代码能够流式读取上游 SSE，但最终会把全部事件存入数组。目标实现应将底层能力拆为：

```text
上游 SSE
  → 增量解析
  → Provider 事件转换
  → UnifiedModelChunk
  → TransformStream / ReadableStream
  → 下游 SSE
```

需要同时支持：

- 背压传播，避免下游读取过慢时持续占用内存；
- 客户端断开后的 `AbortSignal` 取消；
- 首 Token 超时、空闲超时和请求总超时；
- 响应体总大小和单事件大小限制；
- SSE 心跳；
- 下游断开后及时释放 Provider 连接与并发配额；
- 流尾 usage 结算；
- 不记录 Prompt、模型正文和 API Key。

网关核心应提供两种使用方式：

- `stream()`：在线对话和需要实时展示的场景直接透传；
- `complete()`：Agent 工作流在内部消费同一条增量流并聚合为完整结果。

这样可以避免维护两套 Provider 调用逻辑。

## 九、Token 用量与成本计费

建议建立追加式用量流水，至少记录：

- request ID、trace ID、用户和租户；
- Provider、模型、模型连接；
- 路由策略版本和路由原因；
- 输入、输出、缓存命中 Token；
- 单价版本和计算后的费用；
- TTFT、总延迟；
- 重试次数、降级次数和最终状态；
- 创建时间和结算时间。

推荐采用以下结算过程：

1. 请求进入时根据预估输入和最大输出 Token 预占额度；
2. Provider 返回 usage 后使用真实 Token 结算；
3. 请求失败或取消后释放未使用额度；
4. Provider 没有返回 usage 时使用统一 Tokenizer 估算，并标记为 estimated；
5. 定价变更使用新的价格版本，历史账单不得按新价格重新计算。

当前 AgentRun 中的输入、输出 Token 字段可以继续保留为业务运行摘要，但不能替代独立的网关用量流水。

## 十、可观测性

建议使用 OpenTelemetry 统一采集 Trace、Metric 和结构化日志。

### 10.1 Trace

一次模型请求至少包含：

```text
gateway.request
├── admission.rate_limit
├── router.build_route_plan
├── provider.primary.attempt
├── provider.fallback.attempt（可选）
└── usage.settlement
```

### 10.2 Metric

重点指标包括：

- 活跃请求数和活跃 SSE 连接数；
- 请求成功率、429 比例、5xx 比例和超时率；
- TTFT、总延迟的 p50/p95/p99；
- 输入、输出 Token 和费用；
- 路由命中分布；
- 重试率、降级率和熔断状态；
- Redis、数据库连接池和出网代理使用率；
- RSS、CPU 和 Node.js 事件循环延迟。

所有标签都必须控制基数，不得把 request ID、用户输入或完整错误正文作为 Metric 标签。

## 十一、高并发设计与验证口径

### 11.1 已有基础

当前已有以下扩展基础：

- Node.js 异步 I/O；
- BullMQ 分布式任务队列；
- Worker 并发配置；
- Outbox 的 `FOR UPDATE OF o SKIP LOCKED` 并发领取；
- `agent_run_id` 任务去重；
- 数据库终态短路和幂等写入；
- 独立队列 Redis；
- 任务锁、退避和优雅关闭。

这些能力能证明系统具备横向扩展基础，但不能直接证明能够承载某个具体并发数字。

### 11.2 必须验证的两类并发

需要区分：

1. **网关连接并发**：大量长连接 SSE 的网络和内存承载能力；
2. **真实 Provider 并发**：受到 Provider RPM、TPM、并发额度和实际费用限制。

可以使用本地 Stub Provider 验证 1000 条并发 SSE 连接的事件循环、内存和背压表现，但不能把该结果表述成真实 Provider 能够承载 1000 次并发生成。

### 11.3 压测阶段

建议逐档验证：

| 阶段 | 并发连接 | 主要目标 |
| --- | ---: | --- |
| 基线 | 20 | 验证正确性、取消、超时和资源释放 |
| 常规 | 100 | 验证 TTFT、p95、内存和事件循环延迟 |
| 目标 | 150–300 | 验证多副本、Redis、数据库和代理瓶颈 |
| SSE 专项 | 1000 条 Stub 长连接 | 验证流式转发、背压和断开回收 |

压测必须覆盖：

- 正常流式返回；
- 慢客户端；
- 客户端中途断开；
- Provider 429；
- Provider 5xx；
- 首 Token 超时；
- 流中断；
- Redis 短暂不可用；
- 熔断打开和半开恢复；
- 主模型失败后降级成功；
- 所有候选模型不可用。

没有可复现压测报告前，不应在简历或文档中声称“单机支撑 1000+ 并发对话”。完成 Stub SSE 压测后，可以准确表述为“单机承载 1000 条并发 SSE 长连接”；真实模型吞吐量需要另外说明 Provider 和预算边界。

## 十二、建议实施顺序

### 阶段一：流式核心与统一契约

1. 定义统一请求、事件、错误和能力契约；
2. 将当前 OpenAI-compatible 网关改为以 AsyncIterable/Stream 为核心；
3. 保留 `complete()` 聚合接口供现有 Agent 工作流使用；
4. 增加取消、背压和分层超时；
5. 使用 Stub Provider 完成流式行为测试。

### 阶段二：Provider Adapter 与模型注册表

1. 建立 Provider Adapter Registry；
2. 把当前 OpenAI-compatible 实现迁入 Adapter；
3. 根据确认后的 Provider 范围增加 Anthropic 适配器；
4. 定义模型能力、上下文、价格和健康元数据。

### 阶段三：智能路由与高可用

1. 实现硬约束过滤和加权评分；
2. 生成主模型与备用模型 RoutePlan；
3. 实现 RPM、TPM、并发和预算准入；
4. 实现熔断、健康度和降级；
5. 统一网关重试与 BullMQ 重试的总预算。

### 阶段四：用量、成本与可观测

1. 建立用量和费用流水；
2. 接入 OpenTelemetry；
3. 建立路由、延迟、错误和成本面板；
4. 增加告警和异常费用保护。

### 阶段五：压测与容量定值

1. 完成故障注入测试；
2. 完成单实例 SSE 专项压测；
3. 完成多副本真实基础设施压测；
4. 给出 Worker、Redis、数据库、出网代理和 Provider 的容量预算；
5. 将实测结果回写到项目文档和简历表述。

## 十三、可以复用的现有能力

本次改造不应推翻现有实现，以下能力可以直接复用或增量演进：

- `SafeModelEgressClient` 的 SSRF 防护、安全 DNS 解析、固定 IP 连接、TLS SNI、禁止重定向和响应限制；
- 用户模型凭据的 AES-256-GCM 加密保存与 Worker 解密；
- 模型出网审计；
- OpenAI-compatible 请求和 SSE 解析逻辑；
- BullMQ 的任务去重、锁、退避、重试和并发配置；
- Outbox 可靠投递；
- AgentRun 幂等状态机；
- 当前 Token 用量采集；
- Redis 基础设施和已有配额实现经验。

改造重点是把这些分散能力提升为独立、统一、可路由、可观测、可限流的平台服务，而不是重新实现一套与现有安全边界冲突的模型客户端。

## 十四、实施前必须确认的决策

该改造会影响模型接入、数据库 Schema、成本、安全和上线行为。开始编码前必须再次确认以下事项：

1. 首批 Provider 和精确模型 ID；
2. 每个模型是否支持工具调用、JSON、推理内容和长上下文；
3. 网关仅供内部服务使用，还是需要对外提供 API；
4. 路由依据和各因素权重；
5. 用户等级、RPM、TPM、并发和预算策略；
6. 允许的主模型与备用模型降级链；
7. 降级时是否允许质量下降或价格上升；
8. 目标峰值并发、TTFT、p95 和可用性 SLO；
9. Token 定价来源、价格版本和计费精度；
10. 用量流水、路由审计和健康状态的数据留存周期；
11. 是否新增独立网关进程、域名和部署副本；
12. 网关与 Worker 的内部鉴权方式和密钥轮换方案。

未确认上述事项前，可以编写不涉及具体模型和数据库的接口草案与 Stub 测试，但不应自行创建正式数据表、确定模型降级关系或开始真实 Provider 接入。

只有在相关功能和压测均真实完成后，才建议使用以下表述：

> 基于 TypeScript 构建 OpenAI-compatible 多模型统一网关，通过能力约束和成本、延迟、健康度加权实现智能路由；使用 Redis Lua 完成租户及 Provider 维度 RPM/TPM 与并发控制，支持模型级熔断、429/5xx 重试和能力等价降级；采用带背压的 SSE 流式协议转换，并通过 Stub Provider 验证单机 1000 条并发 SSE 长连接，同时使用 OpenTelemetry 观测 TTFT、p95、Token 成本和路由决策。

如果只完成当前已有能力，应采用更保守的表述：

> 实现安全的 OpenAI-compatible 模型调用网关和 BullMQ 异步 Agent 执行链路，支持加密凭据、SSRF 防护、出网审计、SSE 解析、429/5xx 重试、任务幂等及真实 Token 用量回写，为后续多模型路由和容量扩展提供基础。
