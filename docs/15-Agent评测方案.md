# LearnCraft Agent 评测与 LLM Judge 接入方案

> 状态：实施方案（待接入）
>
> 更新时间：2026-10-08
>
> 范围：四个 P0 工作流的评测集生成、五维质量评分和版本对比

## 一、方案结论

LearnCraft 采用“现有业务 Agent + 独立评测运行器 + 独立 LLM Judge”的方案：

- `assessment_generate`、`plan_generate`、`card_content_generate`、`posttest_generate` 继续使用用户自己配置的默认模型；
- 评测运行器是独立进程，负责批量读取评测集、调用现有工作流、调用 Judge 和汇总结果，不参与线上用户任务；
- LLM Judge 只负责生成评测集草稿和评估候选输出，不负责执行业务工作流，不需要自主规划、工具调用或多轮行动；
- Judge 通过独立的 OpenAI 兼容 HTTP 调用访问 Provider，不复用现有 `SafeModelEgressClient`、出网审计或模型限流；
- 评测集、单次评分结果和汇总报告全部保存为仓库文件，不新增数据库表；
- 允许把评测输入、候选输出和评分证据发送给 `.env` 中配置的外部 Provider。

## 二、组件职责

| 组件 | 职责 | 使用的模型配置 |
| --- | --- | --- |
| 现有 Agent Worker | 为用户执行前测、路线、节点内容和节点后测 | 用户在系统中配置的默认模型 |
| 独立评测运行器 | 批量读取用例，调用现有工作流，组织 Judge 评分并生成报告 | 同现有工作流的用户默认模型；不读取 Judge Key |
| LLM Judge | 生成评测集草稿，判断五个质量维度并给出证据 | `AGENT_EVAL_JUDGE_*` 四项环境变量 |

评测运行器不等于新的业务 Agent。它是一个可重复执行的批处理程序，基本流程如下：

```text
读取仓库中的评测集
        ↓
调用现有工作流，生成候选输出
        ↓
执行结构前置检查
        ↓
调用独立 LLM Judge
        ↓
解析五维评分、理由和证据
        ↓
写入单次结果和汇总报告
```

## 三、评测文件布局

建议使用以下仓库目录保存评测资产：

```text
evals/
├─ datasets/       # 固定版本的评测集和参考要点
├─ runs/            # 每次运行的候选输出、Judge 评分和证据
└─ reports/         # 每次运行的汇总报告和版本对比结果
```

文件格式建议使用 JSON 或 JSONL，便于版本管理和批量处理。每条评测用例至少包含：

- `case_id`、工作流类型和评测集版本；
- 学习目标、学习者画像、节点上下文和原始输入快照；
- 必须覆盖的知识点、参考事实和可接受答案要点；
- 五个维度的评分说明和典型错误；
- 可选的历史回归标签。

单次结果至少包含：

- `case_id`、业务 Agent 模型与版本、Prompt/Skill 版本；
- 候选输出和结构前置检查结果；
- Judge 模型与版本；
- 五个维度的分数、理由和证据；
- 加权总分和运行时间戳。

API Key 只能通过未提交的 `.env` 或部署环境注入，不能写入 `evals/` 文件。

## 四、评测集生成

LLM Judge 只生成评测集草稿，草稿必须经过固定规则和人工抽样复核后才能成为黄金评测集：

1. 为四个工作流准备固定模板，包含学习目标、学习者画像、输入上下文、必须覆盖的知识点和典型错误；
2. 使用 Judge 生成候选用例、参考要点、评分说明和难例变体；
3. 执行字段校验、去重、敏感信息检查和基本事实检查；
4. 人工抽样复核正确性和教学适配度；
5. 写入 `evals/datasets/` 并固定版本，后续只追加回归用例，不覆盖已使用版本。

首期建议每个工作流 10 条，共 40 条，覆盖常规、边界和历史低分回归场景。

## 五、五维质量评分

每个维度使用 **1–5 分**：

| 分数 | 含义 |
| --- | --- |
| 5 | 明显达到要求，质量优秀，没有实质问题 |
| 4 | 达到要求，只有轻微问题 |
| 3 | 基本可用，但存在需要修改的问题 |
| 2 | 只有部分内容可用，存在明显问题 |
| 1 | 基本不符合要求，或无法用于当前任务 |

| 维度 | 权重 | Judge 主要检查内容 |
| --- | ---: | --- |
| 正确性 | 3 | 事实、概念、代码、题目答案、解析和因果关系是否正确；不把不确定信息写成确定结论 |
| 完整性 | 2 | 是否覆盖任务目标、关键知识点、必要步骤和要求字段；是否存在关键遗漏 |
| 相关性 | 2 | 是否围绕当前目标、节点、资料和学习者问题；是否出现主题漂移或无关扩展 |
| 可读性 | 2 | 层次、术语、句子、代码、列表和示例是否清楚易读 |
| 教学适配度 | 1 | 难度、解释深度、示例、练习、误区反馈和后测要求是否匹配学习者水平，并支持理解和迁移 |

总权重为 10，程序计算加权平均分：

```text
加权分 = (正确性×3 + 完整性×2 + 相关性×2 + 可读性×2 + 教学适配度×1) / 10
百分制 = 加权分 / 5 × 100
```

Judge 返回五个分项分数、理由和证据；加权分、百分制、平均分、阈值判断和版本差异全部由评测运行器计算。

结构校验、业务校验和安全策略不作为五维质量评分项。校验失败的结果不进入正常质量平均分，但要写入单次结果并标注为无效样本；如需体现端到端影响，可以把该样本的完整性记为 1，并在报告中标注“结构失败”。

## 六、四类工作流的评分重点

| 工作流 | 评分重点 |
| --- | --- |
| `assessment_generate` 前测 | 检查题目、选项、答案和解析正确；覆盖目标知识点；题干和选项易读；难度、诊断性和干扰项符合学习者水平 |
| `plan_generate` 学习路线 | 检查知识依赖和学习顺序正确；路线覆盖学习目标；节点摘要清楚；粒度、难度梯度和前置知识安排适合学习者 |
| `card_content_generate` 节点内容 | 检查概念、代码和示例正确；覆盖 foundation、worked example、误区和来源说明；聚焦当前节点；支持起点适配、概念搭桥、示例陪读和误区修复 |
| `posttest_generate` 节点后测 | 检查题目、答案和解析正确；覆盖关键知识点；只考查已学习内容；题干和反馈易读；难度、迁移要求和错误解释适合学习者 |

## 七、Judge 输入与输出

Judge 输入至少包含：

- 工作流类型；
- 学习目标、学习者画像和节点上下文；
- 原始输入快照；
- 候选 Agent 输出；
- 参考事实、必须覆盖的知识点和可接受答案要点；
- 当前评测规则版本。

如需分析执行过程，可以附加结构化轨迹摘要，例如工具调用结果、校验失败路径、自纠次数和最终状态。Judge 不需要读取或生成隐藏思维链，也不调用 Tavily、数据库或其他外部工具。

建议 Judge 使用 JSON 输出约束，返回以下结构：

```json
{
  "correctness": { "score": 1, "reason": "", "evidence": [] },
  "completeness": { "score": 1, "reason": "", "evidence": [] },
  "relevance": { "score": 1, "reason": "", "evidence": [] },
  "readability": { "score": 1, "reason": "", "evidence": [] },
  "teaching_adaptation": { "score": 1, "reason": "", "evidence": [] }
}
```

## 八、LLM Judge 环境变量

独立评测进程直接使用以下四个环境变量调用 OpenAI 兼容 Provider。业务工作流不会读取或使用这些变量。

```dotenv
# Agent 评测专用 LLM Judge；由独立评测进程直接调用外部 OpenAI 兼容 Provider。
AGENT_EVAL_JUDGE_BASE_URL=
AGENT_EVAL_JUDGE_API_KEY=
AGENT_EVAL_JUDGE_MODEL=
AGENT_EVAL_JUDGE_TEMPERATURE=0
```

| 环境变量 | 含义 |
| --- | --- |
| `AGENT_EVAL_JUDGE_BASE_URL` | OpenAI 兼容 Provider 的接口基地址 |
| `AGENT_EVAL_JUDGE_API_KEY` | Judge Provider API Key，仅在评测进程使用 |
| `AGENT_EVAL_JUDGE_MODEL` | Judge 模型名称 |
| `AGENT_EVAL_JUDGE_TEMPERATURE` | Judge 温度，建议从 `0` 或较低值开始 |

Judge 调用不复用现有 `SafeModelEgressClient`、出网审计和模型限流，评测运行器自行负责请求超时、响应解析和失败重试。Judge 的 Token 和费用只写入评测结果文件，不计入用户 Agent 的用量统计。

本方案允许把评测输入、候选输出、参考要点和评分证据发送到上述配置的外部 Provider。使用外部 Provider 时，评测文件中不得包含 API Key；评测内容是否包含真实用户数据由评测集整理阶段控制。

## 九、执行阶段

### 阶段 A：离线评测

独立评测进程读取 `evals/datasets/`，使用用户默认模型调用现有工作流生成候选输出，再使用 `AGENT_EVAL_JUDGE_*` 调用 Judge。结果写入 `evals/runs/`，汇总报告写入 `evals/reports/`。

### 阶段 B：真实模型抽样

每个工作流抽取常规、边界和回归用例，至少重复 3 次，比较五个维度的平均分和方差。人工复核低分样本，以及 Judge 与人工结论不一致的样本。

### 阶段 C：版本对比

保持评测集和 Judge 配置不变，只替换业务 Agent 的 Prompt、Skill 或默认模型，比较五个维度、加权分和百分制。Judge 模型或评分规则发生变化时，重新建立 baseline。

## 十、评分可靠性控制

- 先用人工评分样本校准 Judge 的 1–5 分标准；
- 正确性评测必须提供参考事实或答案要点，不能只让 Judge 凭常识判断；
- 用不同于业务 Agent 的模型或 Provider 作为 Judge 更稳妥，但不是硬性要求；
- 对固定样本重复评分，检查五维分数和加权分的方差；
- 每次评测抽样人工复核，持续把争议样本加入回归集；
- 不允许 Judge 自己修改评分标准、改变权重或调用外部工具寻找答案。

## 十一、实施边界

本方案不改变四个现有工作流的模型选择，也不把业务工作流迁移到 LangGraph 或其他 Agent 框架。后续实现只需要新增独立评测进程、评测文件目录和 Judge 直连配置，不新增数据库表，也不让业务 Agent 调用 Judge。
