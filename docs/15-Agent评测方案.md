# LearnCraft Agent 评测方案

> 状态：评审稿
>
> 更新时间：2026-10-07
>
> 范围：`apps/agent-worker-ts` 的四个 P0 工作流：`assessment_generate`、`plan_generate`、`card_content_generate`、`posttest_generate`

## 一、评测目标

同时回答四个问题：

1. 输出是否满足现有 JSON 合同，能被业务层安全持久化；
2. 内容是否正确、完整，并符合学习者水平和工作流目的；
3. Agent 的 ReAct、Tavily、校验自纠、重试和幂等行为是否可靠；
4. 延迟、Token、费用、错误率和出网行为是否达到上线要求。

评测以“固定输入 + 固定版本 + 可复现轨迹”为基本单位。每条结果记录工作流、Prompt/Skill 版本、模型与 Provider、schema 版本、工具调用、重试、Token、耗时和最终状态，避免只比较最终文本。

## 二、评测集设计

首期建立 40 条黄金用例，每个工作流 10 条；后续扩展到每个工作流 30 条以上。用例分为：

- **常规集**：覆盖初学者/高级学习者、短目标/长目标、不同语言和不同资料完整度；
- **边界集**：空字段、超长输入、冲突约束、无可用资料、模型输出格式错误、工具超时和重复投递；
- **安全集**：Prompt 注入、要求泄露系统提示词或凭据、恶意 URL、个人信息混入；
- **回归集**：每次修复过的线上问题和历史失败轨迹，固定保留，不得被新版本覆盖。

每条用例至少包含输入快照、预期结构约束、业务评分规则、禁止行为和可接受的答案要点。语义评分不要求唯一参考答案，但必须有可检查的事实和教学标准。

## 三、指标与工作流评分

### 1. 通用指标

| 维度 | 指标 | 说明 |
| --- | --- | --- |
| 合同 | 严格解析通过率、业务校验通过率 | 统计首次输出和自纠后的最终输出；未经校验的结果不得计为成功 |
| 任务 | 工作流成功率、幂等成功率 | 覆盖成功、失败、取消、重试、重复消息和 Worker 重启 |
| Agent 行为 | 平均/最大轮数、工具调用成功率、自纠恢复率、重试/回退率 | 与 `AGENT_REACT_MAX_TURNS_*`、`AGENT_TOOL_MAX_CALLS` 对照 |
| 质量 | 正确性、完整性、相关性、可读性、教学适配度 | 0–4 分；由规则检查 + LLM Judge + 人工抽样校准 |
| 运行 | p50/p95 延迟、输入/输出 Token、估算费用、队列等待、错误率 | 按工作流和模型分别统计 |
| 安全 | 凭据/提示词泄露、越权工具调用、出网策略违规 | 关键安全用例必须全部通过 |

### 2. 工作流专属检查

- **前测 `assessment_generate`**：题量在合同范围内；题目覆盖输入目标；选项、答案和解析一致；干扰项对应常见误区；题目之间不重复。
- **路线 `plan_generate`**：`node_key` 唯一且连续；依赖节点存在且无环；顺序符合学习前置关系；难度和学习者画像匹配；节点摘要足以交接给节点 Agent。
- **节点内容 `card_content_generate`**：`card_content.v2` 字段完整；`worked_example.files`、入口文件和调用顺序一致；示例可运行性线索充分；`pitfalls_debug` 与内容中的真实误区对应；`source_refs` 可追溯。
- **节点后测 `posttest_generate`**：题目只考查已生成节点内容；覆盖关键知识点；不直接泄露答案；解析能解释错误原因；与前测/节点内容的难度变化合理。

建议把单条用例总分设为 100 分：合同与安全 30 分、任务完成 20 分、教学质量 40 分、效率 10 分。合同失败或出现关键安全问题时直接判定该用例失败，不用平均分掩盖。

## 四、执行方式

### 阶段 A：离线回放（每次改 Prompt、Skill、Schema 或模型都执行）

使用现有 Vitest 测试与 fake model/tool gateway，回放评测集并检查合同、业务规则、工具上限、失败恢复和幂等。模型响应使用固定 fixture，保证 CI 稳定；这一阶段不产生真实模型费用。

### 阶段 B：真实模型小样本（合并前或发布前）

从每个工作流抽取常规、边界和安全用例各若干条，使用显式开启的 live integration 配置运行。每条用例至少重复 3 次，记录模型随机性；保存 `AgentRun` 和完整轨迹，人工复核低分样本及所有失败样本。真实测试只允许使用本地开发库和独立队列，不指向生产环境。

### 阶段 C：批量对比（需要时再建设）

以“同一评测集 + 同一输入 + 单一变量”为原则，对比 Prompt/Skill、模型或工具策略。通过 BullMQ 分批执行，使用已有轨迹事件汇总每次运行的质量、延迟、Token、费用和失败原因，生成版本间回归报告。新增评测任务表、报告 API 或费用口径前，另行确认数据保留、模型和预算方案。

## 五、评分与发布门禁

每次评测输出：总分、四个工作流分项分、合同失败列表、质量低分样本、轨迹链接、Token/延迟/费用对比和回归结论。先以当前生产 Prompt/Skill/模型作为 baseline，再评估候选版本。

首期建议门禁如下，具体数值在跑完 baseline 后固化：

- 合同解析和关键安全用例：100% 通过；
- 工作流最终成功率、幂等和错误恢复：不得低于 baseline，且不能引入 P0/P1 回归；
- 教学质量：四类工作流平均分不得低于 baseline，低分样本必须有人工结论；
- 延迟、Token 和费用：单项超过 baseline 的回归需有明确原因和批准记录。

评测报告只允许把“最终通过合同并完成业务持久化”的运行计为成功；模型输出好看但未通过校验、违反安全策略或超出工具/轮数上限，均判定失败。

## 六、落地顺序

1. 先整理 40 条评测集和四类工作流的规则检查器，接入离线回放；
2. 用当前版本跑出 baseline，并校准 LLM Judge 与人工评分的一致性；
3. 接入真实模型小样本和 Agent 轨迹，形成发布前报告；
4. 评测集稳定后，再决定是否建设批量评测队列、报告页面和长期数据存储。

本方案只定义评测口径，不在本次引入新的数据库表、向量模型、Provider 或安全策略；这些会影响架构、成本或上线行为的决策，在实施前单独确认。
