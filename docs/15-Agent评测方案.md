# LearnCraft Agent 评测与 LLM Judge 接入方案

> 状态：实施方案（待接入）
>
> 更新时间：2026-10-07
>
> 范围：四个 P0 工作流的离线评测集生成、五维质量评分和版本对比

## 一、方案结论

LearnCraft 采用“**现有业务 Agent + 独立 LLM Judge**”的双模型方案：

- `assessment_generate`、`plan_generate`、`card_content_generate`、`posttest_generate` 继续使用用户在系统中配置的默认模型连接；
- LLM Judge 只用于生成评测集和评估结果，不参与任何用户业务工作流，不读取用户默认模型连接；
- LLM Judge 采用一次或少量受控的 OpenAI 兼容 Chat Completions 调用，不新增一个具有自主规划、工具调用和多轮行动能力的评测 Agent；
- Judge 的评分结果只包含五个维度：正确性、完整性、相关性、可读性、教学适配度；
- 评测总分由程序根据五个分项分数计算，不能由 Judge 自行计算。

## 二、测评流程

```text
评测集输入
   │
   ├─ 现有工作流 + 用户默认模型 → 候选输出
   │                                  │
   │                                  ├─ 合同/业务前置校验
   │                                  └─ 交给 LLM Judge
   │
   └─ LLM Judge → 生成或补充评测标准
                                      │
                                      ▼
                           五维分数 + 评分理由 + 证据
                                      │
                                      ▼
                             程序确定性汇总报告
```

结构校验、业务校验和安全策略不作为质量评分维度。校验失败的结果不进入正常五维平均分，但应单独记录为无效样本；如果需要反映端到端失败，可以把该样本的完整性记为 0，并在报告中标注“结构失败”。

## 三、评测集生成

LLM Judge 可以根据工作流模板生成评测集草稿，但生成结果不能直接视为黄金标准。流程如下：

1. 为四个工作流准备固定模板，包含学习目标、学习者画像、输入上下文、必须覆盖的知识点和典型错误；
2. 调用 LLM Judge 生成候选用例、参考要点、评分说明和难例变体；
3. 执行去重、字段校验、敏感信息检查和基本事实检查；
4. 人工抽样复核正确性和教学适配度；
5. 固定评测集版本，后续只追加回归用例，不覆盖已使用的版本。

首期建议每个工作流 10 条，共 40 条：常规用例、边界用例和历史低分回归用例均应覆盖。评测集至少包含：

- 输入快照和学习者画像；
- 目标工作流；
- 必须覆盖的知识点和答案要点；
- 五个维度的评分锚点；
- 可接受结果的判定依据；
- 典型错误和不可接受行为。

## 四、五维质量评测

每个维度使用 0–4 分：

| 分数 | 含义 |
| --- | --- |
| 4 | 明显达到要求，没有实质问题 |
| 3 | 基本达到要求，有少量不影响使用的问题 |
| 2 | 部分达到要求，存在需要修改的明显问题 |
| 1 | 大部分不符合要求，只保留少量有效内容 |
| 0 | 完全不符合要求，或无法用于当前任务 |

| 维度 | Judge 主要检查内容 |
| --- | --- |
| 正确性 | 事实、概念、代码、题目答案、解析和因果关系是否正确；不把不确定信息写成确定结论 |
| 完整性 | 是否覆盖任务目标、关键知识点、必要步骤和要求字段；是否存在关键遗漏 |
| 相关性 | 是否围绕当前目标、节点、资料和学习者问题；是否出现主题漂移或无关扩展 |
| 可读性 | 层次、术语、句子、代码、列表和示例是否清楚易读 |
| 教学适配度 | 难度、解释深度、示例、练习、误区反馈和后测要求是否匹配学习者水平，并支持理解和迁移 |

五个维度等权重：

```text
总分 = (正确性 + 完整性 + 相关性 + 可读性 + 教学适配度) / 20 × 100
```

Judge 返回每个维度的分数、理由和证据。总分、通过阈值、平均分和版本差异全部由评测程序计算。

## 五、Judge 输入与输出

Judge 输入至少包含：

- 工作流类型；
- 学习目标、学习者画像和节点上下文；
- 原始输入快照；
- 候选 Agent 输出；
- 参考事实、必须覆盖的知识点和可接受答案要点；
- 当前评测规则版本。

如需分析 Agent 过程，可附加结构化轨迹摘要，例如工具调用结果、校验失败路径、自纠次数和最终状态。Judge 不需要读取或生成隐藏思维链，也不应调用 Tavily、数据库或其他外部工具。

建议 Judge 只返回以下结构，不返回自然语言报告作为唯一结果：

```json
{
  "correctness": { "score": 0, "reason": "", "evidence": [] },
  "completeness": { "score": 0, "reason": "", "evidence": [] },
  "relevance": { "score": 0, "reason": "", "evidence": [] },
  "readability": { "score": 0, "reason": "", "evidence": [] },
  "teaching_adaptation": { "score": 0, "reason": "", "evidence": [] }
}
```

## 六、LLM Judge 环境变量

Judge 单独使用以下四个环境变量，兼容 OpenAI 兼容 Provider。评测命令启动时必须同时填写四项；业务工作流不会读取或使用这些变量。

```dotenv
# Agent 评测专用 LLM Judge；不影响用户默认模型连接。
AGENT_EVAL_JUDGE_BASE_URL=
AGENT_EVAL_JUDGE_API_KEY=
AGENT_EVAL_JUDGE_MODEL=
AGENT_EVAL_JUDGE_TEMPERATURE=0
```

字段含义：

| 环境变量 | 含义 |
| --- | --- |
| `AGENT_EVAL_JUDGE_BASE_URL` | OpenAI 兼容 Provider 的接口基地址 |
| `AGENT_EVAL_JUDGE_API_KEY` | Judge Provider API Key；只在评测进程使用 |
| `AGENT_EVAL_JUDGE_MODEL` | Judge 模型名称 |
| `AGENT_EVAL_JUDGE_TEMPERATURE` | Judge 温度，建议从 `0` 或较低值开始 |

Judge 请求应使用 JSON 输出约束、低随机性、无工具调用和独立的评测请求标识。Judge 的出网请求、Token 和费用应与用户模型调用分开记录，不能混入用户 Agent 的用量统计。

## 七、执行阶段

### 阶段 A：离线评测

使用固定评测集和固定 Judge 配置运行。现有工作流使用用户默认模型生成候选输出，Judge 使用 `AGENT_EVAL_JUDGE_*` 变量评分。先做结构前置检查，再执行五维评分。

### 阶段 B：真实模型抽样

每个工作流抽取常规、边界和回归用例，至少重复 3 次，比较五个维度的平均分和方差。人工复核低分样本，以及 Judge 与人工结论不一致的样本。

### 阶段 C：版本对比

保持评测集、用户输入和 Judge 配置不变，只替换业务 Agent 的 Prompt、Skill 或默认模型，比较五个维度和总分。Judge 版本发生变化时，应重新建立 baseline，避免把评分器变化误判为业务 Agent 变好。

## 八、评分可靠性控制

- 先用人工评分样本校准 Judge 的 0–4 分标准；
- 正确性评测必须提供参考事实或答案要点，不能只让 Judge 凭常识判断；
- 用不同于业务 Agent 的模型或 Provider 作为 Judge 更稳妥，但不是硬性要求；
- 对固定样本重复评分，检查分数方差；
- 每次评测抽样人工复核，持续把争议样本加入回归集；
- 不允许 Judge 自己修改评分标准、改变权重或调用外部工具寻找答案。

## 九、实施边界与待确认事项

本方案不改变四个现有工作流的模型选择，也不把业务工作流迁移到 LangGraph 或其他 Agent 框架。实施 Judge 接入前，需要确认以下会影响模型接入、成本和数据安全的事项：

1. 评测运行器放在现有 `agent-worker-ts` 中，还是作为独立的评测进程；
2. Judge 是否复用现有 `SafeModelEgressClient`、出网审计和模型限流；
3. 评测集和评分结果保存为仓库文件、数据库记录，还是只生成报告；
4. 是否允许把评测输入、候选输出和评分证据发送到配置的外部 Provider。

在这些事项确认前，本文件只作为接入方案，不新增数据库表、不改变用户模型配置，也不让业务 Agent 调用 Judge。


“评测运行器”不是一个新的业务 Agent，而是一个负责批量组织评测流程的程序。
它的职责是：
读取评测集
  ↓
调用现有四类工作流
  ↓
获得候选输出
  ↓
调用独立的 LLM Judge
  ↓
解析五维评分
  ↓
汇总并生成评测报告
例如一条 card_content_generate 评测用例，运行器会：
1. 读取学习目标、学习者画像和节点输入；
2. 使用用户配置的默认模型调用现有节点内容工作流；
3. 获取生成的节点内容；
4. 使用 AGENT_EVAL_JUDGE_* 配置调用 Judge；
5. 得到正确性、完整性、相关性、可读性、教学适配度五项分数；
6. 保存分数、理由和证据。
它与现有业务 Worker 的区别是：
组件	作用
现有 Agent Worker	为真实用户执行前测、路线、节点内容和后测生成
评测运行器	批量执行固定测试样本并调用 Judge 评分
LLM Judge	判断候选输出的五项质量，不负责业务工作流


当前我建议以后把评测运行器做成独立命令或独立进程，这样不会影响线上用户任务，也便于固定评测集、重复运行和比较版本。
