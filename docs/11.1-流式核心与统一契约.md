# LearnCraft 流式核心与统一契约改造方案

> 状态：待审查，尚未实施。
>
> 本文是《11-多模型智能路由与统一网关改造方案》中“阶段一：流式核心与统一契约”的细化设计。
> 本轮只确定改造方案，不修改代码、数据库 Schema、Provider 配置或上线行为。

## 一、目标与结论

当前 `SafeModelEgressClient` 虽然通过 `for await` 增量读取 Provider SSE，但会把每个 JSON 事件加入
`events: unknown[]`，等流结束后再由 `OpenAiCompatibleModelGateway` 统一解析。这会使一次响应同时保留：

- 底层原始 SSE 事件数组；
- 聚合后的正文字符串；
- 聚合后的思考字符串；
- 聚合后的工具调用参数。

目标是把模型调用改成“流式能力为唯一事实源”：

1. Provider SSE 到达后立即增量解析并产出统一事件，不再保存完整原始事件数组；
2. 在线对话正文通过 `stream()` 直接向下游传递，并让下游消费速度反向约束上游读取；
3. `complete()` 不再维护另一套请求逻辑，而是作为 `stream()` 的消费者按需聚合；
4. 工具调用的分片参数必须保留到完整后才能校验和执行；
5. 现有结构化 Agent 工作流仍需要完整正文做 JSON 校验，因此继续使用 `complete()`；
6. 取消、超时、响应大小、错误分类、出网审计和 SSRF 防护必须保持现有安全边界；
7. 现有 Agent 进度 SSE 与未来对话正文 SSE 分开设计，不能把 Redis Pub/Sub 进度通道误当成可靠、
   可背压的正文传输通道。

最终形成两种明确的消费方式：

```text
在线对话助手：stream()   → content.delta → HTTP SSE → 浏览器
现有 Agent 工作流：complete() → 消费 stream() → 聚合正文/工具调用 → 校验与持久化
```

## 二、现有实现与问题定位

### 2.1 Provider 到 Worker

当前链路为：

```text
Pinned HTTPS Response
  → prepareBody 解压
  → readSse 增量拆行
  → JSON.parse
  → events.push(event)
  → 返回 events[]
  → parseStreamCompletion(events)
  → ModelCompletionResponse
```

已有能力包括：

- 固定 IP 连接和原域名 TLS SNI；
- 出网审计 fail-closed；
- 禁止重定向；
- 解压后响应总字节上限；
- `text/event-stream` 校验；
- `[DONE]` 完整性校验；
- 429、5xx 和网络错误分类；
- 正文、思考内容、工具参数和 usage 聚合。

主要问题包括：

1. `readSse()` 返回完整 `unknown[]`，响应越长，内存占用越高；
2. `ModelEgressPort` 只能返回完整事件数组，调用方不能自然使用拉取式消费；
3. `onEvent` 是同步、best-effort 回调，无法表达背压和取消；
4. 当前 `buffer += chunk.toString('utf8')` 没有使用流式 UTF-8 解码器，多字节字符跨网络分片时存在解码风险；
5. 当前解析方式按单行 `data:` 处理，没有形成独立、可测试的 SSE 帧状态机；
6. Provider 流已经到达 Worker，但除思考增量外，正文不能被其他调用方实时消费。

### 2.2 Worker 到 Web

当前 AgentRun 的实时展示链路为：

```text
ModelGateway onReasoningDelta
  → AgentThinkingStream
  → AgentProgressReporter（同步 fire-and-forget）
  → Redis PUBLISH promise 链
  → Web Redis SUBSCRIBE
  → Next.js ReadableStream SSE
  → EventSource
```

这条链路的定位是“临时进度通道”：

- 不落库、不重放；
- Redis 不可用时允许丢失；
- 浏览器断开不能反向暂停 Provider；
- `report()` 不等待发布完成；
- 当前只允许思考增量和步骤元数据，不允许生成正文和工具结果。

因此它不具备端到端背压，也不应该承担未来对话助手的正文流。在线对话助手应使用一次请求内的直接 HTTP SSE
链路；AgentRun 进度通道继续保持“业务执行不依赖浏览器在线”的弱耦合语义。

## 三、范围与非目标

### 3.1 本阶段范围

- 定义统一的模型流事件契约；
- 将 Provider SSE 解析改成 `AsyncIterable` 拉取式接口；
- 实现正文、思考、工具调用、usage 和结束原因的统一增量事件；
- 实现基于统一流的 `complete()` 聚合器；
- 增加 `AbortSignal` 取消传播；
- 明确首字节、空闲和总预算超时的接口位置；
- 保持现有 Agent 工作流的输入、输出和 Token 记账行为兼容；
- 为未来对话助手的直接 HTTP SSE 提供可复用核心，但本阶段不创建对话数据库表。

### 3.2 本阶段非目标

- 不实现智能模型路由；
- 不增加 Anthropic 等新 Provider；
- 不新增模型连接或用量数据库表；
- 不调整模型价格、配额和成本策略；
- 不实现对话助手 UI；
- 不把 Redis Pub/Sub 改成可靠消息队列；
- 不在本阶段宣称已经完成 1000 条 SSE 并发验证。

## 四、统一流事件契约

### 4.1 内部事件类型

建议定义 Provider 无关的判别联合：

```ts
type ModelStreamEvent =
  | {
      type: 'response.started';
      responseId: string | null;
      modelId: string;
    }
  | {
      type: 'content.delta';
      text: string;
    }
  | {
      type: 'reasoning.delta';
      text: string;
    }
  | {
      type: 'tool_call.delta';
      index: number;
      id?: string;
      name?: string;
      argumentsDelta?: string;
    }
  | {
      type: 'usage.updated';
      usage: ModelUsage;
    }
  | {
      type: 'response.completed';
      finishReason: string | null;
      usage: ModelUsage;
    };
```

约束如下：

- 流中最多出现一次 `response.started`；
- `content.delta` 和 `reasoning.delta` 只携带本次增量，不携带累计全文；
- `tool_call.delta` 保留 Provider 的调用索引，用于合并并行工具调用；
- `usage.updated` 可以出现零次或多次，以最后一次为准；
- 只有收到 Provider 正常结束标志并通过完整性校验后，才能产生一次 `response.completed`；
- 异常不伪装成普通流事件，核心层通过抛出 `ModelGatewayError` 表达；
- HTTP SSE 适配层在响应已经开始后，可把异常转换成受控的 `error` SSE 帧再关闭连接。

### 4.2 为什么不直接透传 Provider 原始事件

直接透传会把业务方绑定到 OpenAI 字段，后续无法平滑接入其他 Provider。统一事件层负责：

- 隔离 Provider 字段差异；
- 统一工具调用参数分片；
- 统一 usage 和 finish reason；
- 统一错误码；
- 控制哪些信息可以发送到浏览器；
- 让 `complete()`、HTTP SSE 和测试夹具共同消费同一契约。

### 4.3 浏览器可见事件

内部流事件不应全部原样下发。未来对话助手默认只下发：

```text
message.started
message.delta
message.completed
error
```

下列信息默认不发送给浏览器：

- Provider 原始响应；
- API Key、Base URL 和模型连接 ID；
- 原始工具参数和工具返回；
- 内部路由评分；
- 模型思考原文。

当前 AgentRun 已经存在经用户确认的思考展示能力，可以继续通过原进度契约发送 `thinking.delta`，但不应让该历史行为
自动扩大为所有对话接口的默认行为。

## 五、流式核心接口

### 5.1 出网层接口

将当前一次性返回 `events[]` 的接口改为“打开响应后返回事件流”：

```ts
interface ModelSseResponse {
  statusCode: number;
  events: AsyncIterable<unknown>;
  cancel(reason?: unknown): void;
}

interface ModelEgressPort {
  openOpenAiCompatibleSse(
    input: ModelEgressCallInput,
  ): Promise<ModelSseResponse>;
}
```

`openOpenAiCompatibleSse()` 在返回前完成：

- 出网策略检查；
- allowed 审计；
- TCP/TLS/HTTPS 建连；
- HTTP 状态检查；
- Content-Type 检查；
- Content-Length 预检。

返回后，由 `events` 在消费时完成：

- 解压；
- 解压后总字节计数；
- UTF-8 流式解码；
- SSE 帧解析；
- JSON 解析；
- `[DONE]` 校验。

### 5.2 网关接口

网关以 `stream()` 为核心，`complete()` 是兼容和聚合入口：

```ts
interface ModelGateway {
  stream(request: ModelCompletionRequest): AsyncIterable<ModelStreamEvent>;
  complete(request: ModelCompletionRequest): Promise<ModelCompletionResponse>;
}
```

两者必须复用：

- 同一个请求载荷构造器；
- 同一个受控出网客户端；
- 同一个 Provider 事件归一化器；
- 同一套错误分类；
- 同一套总响应字节限制；
- 同一套取消和超时传播。

禁止保留“流式路径一套解析、完整路径另一套解析”的双实现。

## 六、缓存与聚合边界

“实时输出不缓存”具体定义如下。

### 6.1 流式核心允许保留的状态

底层解析器只允许保留有界的协议状态：

- 未组成完整 UTF-8 字符的少量字节；
- 未组成完整 SSE 帧的尾部文本；
- 当前总接收字节数；
- 是否收到 `[DONE]`；
- 当前响应状态机；
- 必要的 Provider 事件序号。

不得保留：

- 全部原始 Provider 事件；
- 完整正文；
- 完整思考内容；
- 已经向下游交付的普通增量。

协议尾部缓冲必须设置单事件上限，不能只依赖整个响应 8MB 上限，否则 Provider 长时间不发送换行时仍可能造成大字符串占用。

### 6.2 `complete()` 允许聚合的状态

`complete()` 是独立消费者，可以根据调用场景有界聚合：

- 最终正文：现有四个结构化 Agent 工作流必须依赖它做 JSON 解析与校验；
- 思考内容：现有工具轮需要把 assistant 消息继续加入同一 ReAct 会话，且当前进度契约需要轮次完整思考；
- 工具调用 ID、名称和分片参数：必须完整合并后才能校验和执行；
- 最终 usage；
- finish reason。

这不属于底层 SSE 原始事件缓存，而是调用方显式选择的业务聚合。聚合结果仍受总响应字节上限和字段级上限保护。

### 6.3 工具调用的特殊边界

工具调用参数不能边到达边执行。例如：

```text
第 1 片：{"que
第 2 片：ry":"TypeScript
第 3 片： SSE"}
```

必须按 `index` 合并，等待 Provider 明确结束工具调用后再进行：

1. ID 和函数名完整性校验；
2. 参数字符串长度校验；
3. JSON 解析；
4. 工具白名单校验；
5. 工具参数 Schema 校验；
6. 实际执行。

原始工具参数不得通过对话正文 SSE 发送到浏览器。

## 七、背压模型

### 7.1 Provider 到网关

`PinnedHttpResponse.body` 已经是 `AsyncIterable<Buffer>`。改造后不再主动把所有事件读入数组，而是只在消费者请求下一项时读取：

```text
消费者 next()
  → 网关请求下一个统一事件
  → SSE 解析器请求下一帧
  → Node Readable 读取有限字节
```

Node.js Readable 仍可能在自身 `highWaterMark` 范围内预读，这是有界传输缓冲，不等同于应用层全响应缓存。

### 7.2 网关到浏览器

未来直接 HTTP SSE 适配器应使用 `TransformStream` 或等价的可等待写入接口：

```ts
await writer.ready;
await writer.write(encodedFrame);
```

只有下游具备消费能力时才继续从 `ModelStreamEvent` 迭代器读取，从而形成：

```text
浏览器读取速度
  → HTTP 响应写入速度
  → ModelStreamEvent 消费速度
  → Provider 响应读取速度
```

禁止在 HTTP 适配层另建无界数组或无界 Promise 链。

### 7.3 Redis 进度通道不是背压链路

现有 `AgentProgressReporter.report()` 是同步 fire-and-forget，Redis Pub/Sub 也没有消费确认。因此：

- 浏览器慢不能暂停 AgentRun；
- 浏览器断开不能取消已经排队的 Agent 工作；
- 思考增量允许丢失；
- 步骤事件仍由最终状态轮询兜底；
- 该通道只能采用有界队列、丢弃或限速保护，不能宣称端到端背压。

这是合理的职责差异：后台 AgentRun 不应该因为用户关闭页面而停止；在线对话请求则应该在客户端断开时立即取消。

## 八、取消与资源释放

### 8.1 统一取消信号

`ModelCompletionRequest` 建议增加：

```ts
signal?: AbortSignal;
```

信号依次传播到：

```text
HTTP Request
  → ModelGateway.stream
  → SafeModelEgressClient
  → PinnedRequester
  → ClientRequest / TLS Socket / 解压 pipeline
```

取消时必须：

- 停止继续读取 Provider；
- 销毁 HTTPS 请求与底层 socket；
- 停止解压 pipeline；
- 调用异步迭代器的 `return()`；
- 释放未来可能持有的并发额度；
- 不继续执行工具；
- 返回稳定的 `MODEL_REQUEST_ABORTED`，且标记为不可自动重试。

### 8.2 不同业务的取消语义

- 在线对话：浏览器断开即取消模型请求；
- 当前 AgentRun：页面断开只关闭进度订阅，不取消后台任务；
- 用户主动点击“取消 AgentRun”：需要由任务取消状态向正在执行的 Worker 传播信号，这是独立于本阶段流式核心的后续改造。

## 九、超时设计

建议把当前单一读超时拆成四类预算：

| 超时 | 起止范围 | 作用 |
| --- | --- | --- |
| connect timeout | 建连至 TLS 完成 | 防止网络建连长期阻塞 |
| first-event timeout | 请求发出至首个合法事件 | 约束首 Token 等待 |
| idle timeout | 相邻数据块或事件之间 | 发现流中途卡死 |
| total timeout | 整次 Provider 尝试 | 控制最坏延迟和成本 |

具体默认值会影响上线行为，实施前必须结合现有工作流最长生成时间确认，并继续通过环境变量注入，不能硬编码。

## 十、重试边界

流式请求能否重试取决于结果是否已经对外可见。

### 10.1 `stream()`

- 在产生第一个对外事件前遇到 429、5xx 或网络错误，可以按现有策略重试；
- 一旦正文、思考或工具增量已经交给调用方，就不能静默重试并把另一条流接在后面；
- 流开始后失败，应抛出稳定错误，由 HTTP 适配层发送 `error` 帧并结束连接；
- 后续模型降级同样只能发生在首个对外增量之前。

### 10.2 `complete()`

- 没有任何增量观察者时，失败尝试的局部聚合可以丢弃并整体重试；
- 如果通过兼容回调向现有进度通道发送过思考增量，该尝试已经对用户可见，透明重试可能产生重复展示；
- 首期兼容方案可以继续依靠轮次结束的 `thinking.completed` 覆盖成功尝试的增量，但必须记录 attempt，测试重复片段；
- 更严格的后续方案是增加 `attempt.started/attempt.reset` 事件，让前端按 attempt 清空失败尝试；本阶段不强制扩大进度协议。

网关重试与 BullMQ 整体任务重试必须分别保留，但后续需要统一总预算，避免多层重试相乘。

## 十一、SSE HTTP 契约草案

未来对话助手可使用以下响应头：

```http
Content-Type: text/event-stream; charset=utf-8
Cache-Control: no-cache, no-transform
Connection: keep-alive
X-Accel-Buffering: no
```

正文帧示例：

```text
event: message.delta
data: {"v":1,"seq":1,"text":"你好"}

event: message.delta
data: {"v":1,"seq":2,"text":"，有什么可以帮助你？"}

event: message.completed
data: {"v":1,"seq":3,"finish_reason":"stop","usage":{"input_tokens":100,"output_tokens":12}}

```

流开始后的错误示例：

```text
event: error
data: {"v":1,"code":"MODEL_PROVIDER_STREAM_INTERRUPTED","retryable":true}

```

约束：

- SSE 帧只能携带经过白名单转换的字段；
- 不返回 Provider 错误原文；
- `seq` 在单次 HTTP 响应内单调递增；
- `message.completed` 只表示 Provider 正常完成且 usage 已结算；
- 浏览器收到 `error` 或连接非正常关闭时，不应把已收到的半截回答标记为完整答案；
- 心跳只用于维持 HTTP 连接，不计入模型事件序列。

## 十二、接入现有 Agent 流程

### 12.1 保持现有业务入口不变

四个现有工作流仍调用：

```ts
complete(request): Promise<ModelCompletionResponse>
```

内部改为：

```text
complete(request)
  → for await (event of stream(request))
  → ModelCompletionAccumulator.accept(event)
  → accumulator.finish()
  → ModelCompletionResponse
```

因此以下上层行为保持不变：

- `runReactAgentSession` 仍获得完整 assistant 消息；
- 工具参数仍在执行前完整合并；
- 工具成功或失败仍追加到同一会话；
- 工作流最终 JSON 仍进行完整 Schema 校验；
- Token 仍由工作流累计并写回 AgentRun；
- `finish_reason=length` 仍归类为不可重试的截断错误；
- 既无正文也无工具调用仍视为非法响应。

### 12.2 思考增量兼容

首期保留 `ModelCompletionRequest.onReasoningDelta` 兼容字段：

```text
reasoning.delta
  → complete() 消费事件时调用 onReasoningDelta
  → AgentThinkingStream.push
  → thinking.delta
```

它只用于现有 Agent 进度展示，不作为新流式核心的主要接口。完成现有调用链迁移后，可再决定是否用统一事件观察器替代该专用回调。

### 12.3 `thinking.completed` 兼容

当前前端使用一轮完整思考覆盖增量，且 ReAct 工具轮可能需要把 reasoning 内容放回 assistant 消息。因此
`complete()` 首期继续聚合 reasoning，完成后沿用 `thinking.completeTurn()`。

直接 `stream()` 模式不聚合完整 reasoning，也不产生 `thinking.completed`；如果某个调用方需要完整思考，必须显式选择聚合消费者。

### 12.4 未来对话助手接入

对话助手不应经过 BullMQ 和 Agent 进度 Pub/Sub，而应采用请求内直连：

```text
浏览器 POST 对话消息
  → Web 校验用户、会话和当前页面上下文
  → Context Builder 组装消息
  → ModelGateway.stream
  → Web HTTP SSE 直接返回 content.delta
  → 完成后由对话应用服务保存最终 assistant 消息
```

对话消息表结构、上下文留存、最终回答持久化和断线恢复会影响数据库与隐私策略，必须在实现对话功能前单独确认；
本阶段只提供流式核心，不创建相关 Schema。

## 十三、建议的代码改造位置

## 十四、实施步骤

### 步骤一：先建立字符级和协议级解析器

1. 使用 `TextDecoder` 的流式模式或 Node `StringDecoder` 处理跨 chunk UTF-8；
2. 按 SSE 空行边界组装事件，而不是把每个网络 chunk 当成事件；
3. 保留 data-only Provider 约束；
4. 增加单事件字节/字符上限；
5. 保留解压后总字节上限和 `[DONE]` 校验；
6. 用异步生成器逐条 yield，不创建 `events[]`。

### 步骤二：建立 Provider 事件归一化器

1. 将 OpenAI `choices[0].delta.content` 转为 `content.delta`；
2. 将 `reasoning_content` 转为 `reasoning.delta`；
3. 将工具调用分片转为 `tool_call.delta`；
4. 将流尾 usage 转为 `usage.updated`；
5. 校验 finish reason 并产生 `response.completed`。

### 步骤三：实现 accumulator 和 `complete()`

1. 用 Map 按工具调用 index 聚合；
2. 聚合现有工作流所需的正文和 reasoning；
3. 保留当前错误码与响应类型；
4. 在消费 reasoning 增量时调用现有兼容回调；
5. 将现有 `parseStreamCompletion(events)` 测试迁移到 accumulator 测试。

### 步骤四：接入现有工作流

1. 保持四个工作流调用签名不变；
2. 回归工具循环、校验失败自纠和 Token 累计；
3. 回归思考增量与权威整段；
4. 回归 Provider 重试和 BullMQ 任务重试；
5. 确认不新增业务写入和数据库迁移。

### 步骤五：增加直接 HTTP SSE 适配器

该步骤用于后续对话助手，在对应产品和数据决策确认后实施：

1. 用户、对话和页面上下文鉴权；
2. `content.delta` 到 SSE 帧的白名单转换；
3. 等待式写入与背压；
4. 请求断开传播 AbortSignal；
5. 正常结束、流中错误和不完整回答状态；
6. 最终 assistant 消息的持久化策略。

## 十五、测试与验收矩阵

### 15.1 SSE 解析

- 一个 JSON 事件被拆成多个网络 chunk；
- 一个 chunk 包含多个 SSE 事件；
- 中文 UTF-8 字符在字节中间被拆开；
- `\r\n` 和 `\n`；
- keep-alive 注释；
- 非 data 行；
- 空 data；
- 非法 JSON；
- 尾部残缺；
- 缺少 `[DONE]`；
- 只有 `[DONE]` 没有业务事件；
- 单事件超限；
- 解压后总响应超限；
- gzip/deflate/br 解压异常。

### 15.2 统一事件

- 正文增量顺序不变；
- reasoning 增量顺序不变；
- 多个工具调用按 index 分离；
- 同一个工具参数跨多个分片正确合并；
- usage 以流尾值为准；
- `finish_reason=length` 仍报截断；
- 没有正文且没有工具调用时报非法响应；
- 只有正常结束才产生 `response.completed`。

### 15.3 背压与取消

- 慢消费者下不会生成与响应长度线性增长的应用层数组；
- 消费暂停时读取保持在 Node 流高水位附近；
- 浏览器断开后 Provider socket 被关闭；
- Abort 期间不执行后续工具；
- 取消错误不重试；
- 解压 pipeline 和迭代器均能释放。

### 15.4 现有流程回归

- 四个 `run_type` 的结构化结果不变；
- 工具调用参数不丢失；
- 工具调用数上限不变；
- 校验失败回灌与同会话自纠不变；
- thinking.delta 仍逐段到达；
- thinking.completed 仍能覆盖增量；
- Token 累计和 AgentRun 回写不变；
- Provider 429/5xx 重试行为有明确测试；
- 重复任务投递仍不产生重复业务写入。

### 15.5 内存验收

使用 Stub Provider 返回不同长度但相同分片大小的 SSE：

- `stream()` 模式下，RSS 增量不应与完整响应长度线性增长；
- `complete()` 模式下，内存只随需要聚合的最终正文、reasoning 和工具参数增长，不再额外保存一份原始事件数组；
- 慢客户端测试必须记录 RSS、事件循环延迟和 socket 释放时间；
- 在没有实测数据前不填写具体性能提升百分比。

## 十六、风险与取舍

### 16.1 `complete()` 仍会保存完整正文

这是现有结构化 Agent 工作流的必要条件，因为工作流必须在最终 JSON 完整后才能进行 Schema 校验和业务写入。
本次优化消除的是底层原始事件副本，并为实时调用提供不聚合路径，不承诺所有业务都做到零全文内存。

### 16.2 工具参数必须缓冲

工具参数是分片 JSON，提前执行会造成安全和正确性问题。必须设置单次工具参数长度上限，完整后再校验。

### 16.3 真正背压只存在于直接链路

HTTP 请求内的 Provider → Gateway → Browser 可以传播背压；Redis Pub/Sub 进度链路不能。强行让后台 AgentRun
等待浏览器会破坏任务可靠性，因此不建议统一两种语义。

### 16.4 流开始后的错误无法改 HTTP 状态码

HTTP 响应头一旦发出，后续错误只能通过 SSE `error` 帧和连接关闭表达。调用方必须区分“完整回答”和“已经显示但未完成的回答”。

### 16.5 重试可能造成已展示增量重复

直接正文流在首个增量后禁止透明重试。现有思考进度兼容路径如果保留重试，需要依靠完整轮次覆盖或后续 attempt
协议清理重复内容。

## 十七、审查时需要确认的事项

在开始编码前，请重点确认：

1. 是否接受 `stream()` 为核心、`complete()` 为流消费者的结构；
2. 是否接受当前四个结构化工作流继续通过 `complete()` 聚合完整正文；
