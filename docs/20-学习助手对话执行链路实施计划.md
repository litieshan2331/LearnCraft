# 学习助手对话执行链路实施计划

## 一、计划目标

打通以下最小闭环：

```text
页面发送消息
  → Web 保存用户消息并创建 queued 运行
  → 投递学习助手队列
  → Worker 消费运行并执行 LangGraph
  → 助手消息与运行结果落库
  → 页面读取助手回复和运行状态
```

本计划对应 [17-学习助手对话 MVP 方案](./17-学习助手对话MVP方案.md) 中“数据库建模后的剩余实施步骤”的第 7、8、9 项。实施顺序是先完成服务端真实执行链路，再接入页面，最后做端到端验收。

以下内容已经具备，后续步骤直接复用，不重新设计：

- [x] 学习助手会话、消息、对话运行和学习经历记忆表。
- [x] Repository 和应用服务。
- [x] 创建会话、读取会话、发送消息、读取消息、查询运行状态 API。
- [x] LangGraph.js 主图和 PostgreSQL Checkpointer。
- [x] 主 Agent、错题归因 Agent、苏格拉底导师 Agent。
- [x] 业务工具、Skill、Tavily、结构化输出校验和证据验证端口。
- [x] 主 Agent 与子 Agent 独立 ReAct 轮数上限。
- [x] 消息和学习经历的幂等写入合同。
- [x] 假模型下的图恢复、工具调用、消息持久化和相关测试。

当前已知缺口：Worker 已经可以执行 LangGraph，并通过鉴权内部 API 读取上下文、回写消息和运行结果；前端真实链路与端到端验收仍待后续阶段。

## 三、执行清单

### 第一步：增加学习助手队列任务处理器

**对应 MVP 清单：第 7 项——接入对话运行的队列投递与 Worker 消费。**

- [x] 确认现有 BullMQ 队列、Job 数据结构、重试和退避约定。
- [x] 定义学习助手 Job 载荷：`run_id`、`conversation_id`、`owner_id`、触发消息 ID、连接 ID 和模型 ID。
- [x] 使用 `run_id` 作为 Job 幂等键，重复投递不创建重复任务。
- [x] 增加学习助手队列投递端口。
- [x] 在发送消息事务中同时写入 PostgreSQL Outbox；Dispatcher 最终投递 Job，投递失败按 Outbox 退避并可恢复。
- [x] 增加 Worker 处理器，领取 `queued` 运行并原子改为 `running`。
- [x] 保持同一会话同一时间只有一个 `queued` 或 `running` 运行。
- [x] 处理队列重试、Worker 崩溃和已结束运行重复领取。

**完成标准：** 发送消息后，运行状态可以从 `queued` 进入 `running`；重复投递不会并行执行同一运行。

### 第二步：装配 LangGraph Worker

**对应 MVP 清单：第 7 项——Worker 执行 LangGraph。**

- [x] Worker 根据运行记录通过 Web 内部接口装配本次已确定的模型连接，并在 Worker 内解密凭据。
- [x] 恢复同一 `conversation_id` 对应的 PostgreSQL Checkpoint（`thread_id = conversation_id`）。
- [x] 装配 `PgLearningAssistantRuntimeStore` 和学习助手完整轨迹写入器。
- [x] 装配错题事实、Skill、Tavily 和消息持久化端口；画像、掌握度和学习经历验证端口留在下一步内部 API 扩展。
- [x] 调用 `createLearningAssistantGraph(deps)` 和 `runLearningAssistant(graph, deps, input)`。
- [x] Worker 重试时复用同一个 `run_id`、`conversation_id` 和幂等标识。
- [x] 不把模型连接密钥写入 Job、Checkpoint、消息表或公开 API。
- [x] 图成功后写入助手消息、运行统计和成功状态；图失败后写入安全错误状态。

**完成标准：** Worker 能在假模型下完成普通编程问题、错题归因和导师追问，并能从 PostgreSQL Checkpoint 恢复。

### 第三步：实现 Worker 内部 API

**对应 MVP 清单：第 5、6、7 项——业务上下文、权限、错误记录和结果回写。**

#### 上下文读取接口

- [x] 读取当前会话绑定的错题事实。
- [x] 读取用户画像。
- [x] 读取用户掌握度。
- [x] 读取必要的学习上下文和历史学习经历。
- [x] 读取最近 20 轮消息，当前轮必须包含在内。
- [x] 根据服务端反查的 `owner_id`、`conversation_id` 和 `question_id` 绑定数据。
- [x] 拒绝模型或 Job 参数自行指定其他用户、题目或会话。

#### 结果回写接口

- [x] 回写助手消息和必要的工具消息。
- [x] 回写模型调用次数、Token、子 Agent、Skill、Tavily 和错误摘要。
- [x] 回写运行成功、失败或取消状态。
- [x] 回写通过服务端证据校验的学习经历。
- [x] 所有消息、运行统计和学习经历写入保持幂等。
- [x] 原始模型和工具轨迹只进入内部观测表，不进入公开消息响应。

**完成标准：** Worker 不直接绕过业务边界写表；所有上下文读取和结果回写都经过鉴权的内部端口。

### 第四步：打通运行状态闭环

**对应 MVP 清单：第 7 项——页面发送消息到页面读取回复的完整链路。**

- [x] 发送消息 API 返回 `202` 和 `run_id` 后，事务内写入学习助手 Outbox，由 Dispatcher 自动产生唯一 Job。
- [x] 页面可以查询 `GET /runs/{run_id}` 获得 `queued`、`running`、`succeeded` 或 `failed`。
- [x] Worker 成功后，助手消息通过消息分页 API 读取；页面历史不受上下文窗口限制。
- [x] Worker 失败后，运行接口只返回安全错误文案，详细错误只保留在内部轨迹。
- [x] 页面刷新后可以根据 `conversation_id` 和 `active_run_id` 恢复消息与运行状态。
- [x] 同一会话存在运行时继续拒绝新的并发消息，运行结束后才允许发送下一轮。
- [x] 同一 `run_id` 使用 PostgreSQL session advisory lock 串行执行；重复 Job 在锁处等待，前一执行结束后检查终态，Worker 崩溃释放连接后才允许从同一 `thread_id` 和 Checkpoint 恢复；重试耗尽后才写入 `failed`。

**完成标准：** Web API、Outbox、BullMQ、Worker 和假模型的单元/集成合同已覆盖“发送一条消息并读取助手回复”、状态查询、刷新恢复、并发限制、失败安全文案及 Checkpoint 重试恢复。需要连接 PostgreSQL/Redis 的真实环境验收仍由第五步端到端清单执行。

### 第五步：接入前端和端到端验收

**对应 MVP 清单：第 8、9 项——学习起点页面和端到端验收。**

#### 页面接入

- [ ] 在“学习起点”增加学习助手入口。
- [ ] 创建或恢复学习助手会话。
- [ ] 展示全部历史消息，使用游标分页加载，不把页面历史限制为 20 轮。
- [ ] 发送消息后展示排队中、运行中、成功和失败状态。
- [ ] 成功后刷新并展示助手回复。
- [ ] 当前阶段、待回答问题和提示级别按公开接口展示。
- [ ] 不向用户展示长期记忆原文、内部工具载荷或完整模型轨迹。

#### 端到端验收

- [ ] 普通编程问题可以直接回答。
- [ ] 错题问题可以完成“归因 → 导师”串行调用。
- [ ] 每轮最多一个主要问题，允许没有问题的完整回答。
- [ ] 用户连续未推进时提示级别升级。
- [ ] 用户实际修复后可以进入验证流程。
- [ ] 证据不足时返回 `insufficient_evidence`，不写入错误记忆。
- [ ] 工具失败、模型失败和结构化校验失败可以区分记录。
- [ ] Worker 崩溃后恢复 Checkpoint，不重复已完成的幂等写入。
- [ ] 重复 `Idempotency-Key` 不重复创建用户消息和运行。
- [ ] 页面保留完整历史，模型只使用最近 20 轮上下文。

**完成标准：** 在测试数据库和假模型环境下，完整验证页面发送、队列消费、LangGraph 执行、回复落库、状态查询、刷新恢复和异常恢复。

## 四、一次执行顺序

后续每次只推进一个清单阶段，顺序固定为：

1. 第一步：队列任务处理器。
2. 第二步：LangGraph Worker 装配。
3. 第三步：Worker 内部 API。
4. 第四步：运行状态闭环。
5. 第五步：前端接入与端到端验收。

每个阶段完成后先运行对应单元测试和类型检查，再进入下一阶段；不在未完成队列消费链路前提前实现页面交互。

第一步至第四步已完成。下一项是**第五步：接入前端和端到端验收**：在学习起点接入会话 UI，并在测试 PostgreSQL、Redis 和假模型环境中执行完整链路验收。
