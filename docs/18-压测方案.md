# LearnCraft 压测方案（第一版）

> 状态：待执行
>
> 日期：2026-10-11
>
> 范围：`assessment_generate`、`posttest_generate`、`plan_generate`、`card_content_generate` 的端到端异步链路

## 一、目标与范围

验证以下链路在并发和排队场景下是否稳定：

```text
创建 AgentRun → Outbox → BullMQ 队列 → Agent Worker → 模型调用 → 数据库写回
```

本版重点观察：

- 短任务池与长任务池是否互相影响；
- Redis 并发、RPM 限流和队列退避是否生效；
- PostgreSQL 连接数是否随模型等待时间异常增长；
- Worker 扩容或重复投递时是否出现重复执行、丢任务或卡死；
- 在不同并发下的吞吐、排队时间和端到端延迟。

本版不评价模型回答质量，也不直接对生产环境施压。

## 二、执行前置条件

1. 使用独立的本地或 staging 环境，完成数据库迁移，确认 Web、Dispatcher、Worker、PostgreSQL 和两个 Redis 均为 `ready`。
2. 准备可重复使用的测试学习目标、路线节点和测试账号。测试账号数量应不小于并发用户数，避免单用户限流成为唯一瓶颈。
3. 记录执行时的 Git commit、Compose 配置和以下实际值：短/长任务并发、Worker 副本数、模型全局并发、API Key 与用户限流、任务重试参数、各工作流最大轮数。
4. 先使用模拟模型或可控测试 Provider 完成容量摸底；真实 Provider 只执行小规模验证。真实压测前必须另行确认 Provider、模型、上游限额和费用预算，本方案不替这些参数做默认选择。
5. 第一轮关闭 Tavily 或固定其响应，避免联网工具延迟和额度波动干扰基础链路；工具熔断与额度场景放到故障注入阶段。

## 三、压测入口

压测程序通过现有登录态调用四个创建接口，并轮询 AgentRun 状态：

| 工作流 | 创建接口 | 资源池 |
| --- | --- | --- |
| `assessment_generate` | `POST /api/v1/learning-goals/{goal_id}/assessment-runs` | 短任务池 |
| `posttest_generate` | `POST /api/v1/plan-nodes/{node_id}/post-assessment-runs` | 短任务池 |
| `plan_generate` | `POST /api/v1/learning-goals/{goal_id}/plans` | 长任务池 |
| `card_content_generate` | `POST /api/v1/plan-nodes/{node_id}/content-runs` | 长任务池 |

每次创建请求使用新的 `Idempotency-Key`，保存返回的 `agent_run_id`，然后轮询：

```text
GET /api/v1/agent-runs/{agent_run_id}
```

轮询到 `succeeded`、`failed`、`cancelled` 或 `expired` 后结束该样本。请求体使用各接口现有 Schema 和固定测试夹具，不在压测脚本中复制业务规则。

## 四、场景与负载

每个场景先预热 30 秒，再正式采样；正式采样至少保留 1 分钟或完成 20 个样本，以先达到者为准。

| 场景 | 负载 | 目的 |
| --- | --- | --- |
| 冒烟 | 四类工作流各 1 个样本 | 检查环境、数据和结果写回 |
| 单池基线 | 每类工作流并发 1，完成 5 个样本 | 获得无排队基线 |
| 单池阶梯 | 并发 `1 → 2 → 4 → 8`，短池和长池分别执行 | 找到各资源池的容量拐点 |
| 混合流量 | 短任务/长任务按 `70%/30%`，总并发从 `4` 增至 `8` | 验证资源隔离与整体吞吐 |
| 突发流量 | 10 秒内提交一批总并发 2 倍的任务，再观察 5 分钟 | 验证削峰、退避和 backlog 恢复 |
| 故障注入 | 模拟 Provider 429/5xx、Worker 重启、Redis 短暂不可用 | 验证重试、回退、幂等和故障恢复 |

如果真实 Provider 的限额低于上述并发，阶梯场景改用模拟模型；真实 Provider 只保留冒烟、基线和低并发限流验证。

## 五、采集指标

压测程序至少记录以下时间点：请求发送、AgentRun 创建、进入运行、终态写回。报告按工作流和场景分别统计：

- 创建接口成功率、HTTP 状态和延迟；
- 队列等待时间、Worker 执行时间、端到端完成时间的 p50/p95/p99；
- 吞吐量（成功任务数/分钟）、失败率、取消率、超时数；
- 队列深度、重试次数、429/5xx 次数、限流等待次数；
- Worker CPU、RSS、事件循环延迟和副本数；
- PostgreSQL 活跃/峰值连接、慢查询和连接池等待；
- Redis 内存、命令延迟、队列键数量和限流键数量；
- 输入/输出 Token、模型调用次数和实际费用（Provider 可提供时）。

业务一致性检查从 `agent.agent_runs`、`agent.agent_run_events`、结果表和观测事件中完成：每个样本必须有且只有一个终态，不能出现重复结果、孤儿队列任务或长时间停留在 `queued/running` 的任务。

## 六、首版验收口径

首版先形成真实基线，不预设最终 SLA。满足以下条件才算通过该轮：

- 冒烟样本全部完成，结果结构校验通过；
- 正式样本无未解释的 5xx、数据丢失、重复写回或永久卡住；
- 长任务持续排队时，短任务仍能被短任务池处理；
- Provider 429/5xx 不会突破 Redis 限流和配置的重试上限；
- Worker 重启或重复投递后，AgentRun 最终只产生一份有效结果；
- 压测结束后队列 backlog 在约定观察窗口内恢复为零或回到基线；
- PostgreSQL 连接、Redis 内存和 Worker RSS 没有随排队时间持续失控增长。

容量结论使用“达到哪一级并发、对应 p95 和资源峰值、何时出现排队或错误”描述，不直接宣称系统支持某个固定并发数。

## 七、执行产物与顺序

后续实现压测程序时，每次运行写入独立目录，例如 `tmp/load-test/<日期>-<场景>/`，至少包含：原始样本、按工作流汇总、失败样本、配置快照和结论 Markdown。文件中不得写入 API Key、Cookie、模型密钥或完整敏感 Prompt。

执行顺序固定为：

1. 环境健康检查和配置快照；
2. 冒烟与单池基线；
3. 单池阶梯和混合流量；
4. 突发流量与故障注入；
5. 清理测试数据，生成报告；
6. 根据容量拐点调整 Worker、队列、Redis 或数据库连接池后，用同一场景复测。
