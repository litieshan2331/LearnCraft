# 四个工作流的备用模型与熔断方案

> 状态：待审查；只讨论现有 OpenAI-compatible 工作流，不改代码、数据库或上线配置。

## 结论

建议为每位用户显式配置一个备用模型连接，并在模型调用层增加共享熔断状态：主连接发生可恢复故障时，优先遵守有限重试；若达到切换条件且备用连接健康，则改用备用连接完成本次调用。切换后，同一 AgentRun 后续轮次固定使用备用连接，避免一段 ReAct 会话频繁变换模型。

## 大致流程

```text
读取当前用户的主连接与已授权备用连接
  → 校验连接状态、工具调用和结构化输出等所需能力
  → 检查主连接熔断状态、获取现有 Redis 限流许可
  → 调用主模型；超时／网络错误／5xx 达到阈值后切换备用
  → 备用成功：继续工作流；都失败：交给现有 BullMQ 任务重试
```

1. **备用连接**：只允许使用同一用户事先授权的 `active` 连接，继续走凭据解密、受控出网与审计。备用可配置为另一 OpenAI-compatible 模型；不支持所需工具或输出能力时不切换，不静默删减请求。切换是一次 `complete()` 的模型选择，不改变工作流最终 JSON 校验要求。
2. **熔断**：按“模型连接 ID + 模型 ID”在 Redis 中共享状态，供多个 Worker 副本共同判断。只把网络超时与上游 5xx 计入故障；达到可配置阈值后暂时打开，冷却结束允许少量半开探测，成功关闭、失败重新打开。429 优先视为该凭据的限流冷却，不计入所有用户共享的故障；参数错误、鉴权错误和安全出网拒绝不触发熔断。
3. **预算与可追踪性**：同一次模型调用必须限制总尝试次数和等待时间，不能让“主模型重试 × 备用重试 × BullMQ 重试”无限放大。现有 Redis 并发/RPM 限流对主、备每次实际请求分别生效；记录主备连接、切换原因、尝试次数和可取得的用量，避免把失败尝试误报为零成本。

当前网关只对传入连接重试，工作流只读取默认连接；AgentRun 虽有 `fallback_reason` 字段，但尚无备用连接关系、熔断状态和切换写入逻辑。内部 `complete()` 会聚合完整输出；若主模型在 SSE 中途失败，可以丢弃本轮未提交的正文并重新调用备用，但已临时推送的思考增量可能已经被看到，不能承诺无痕切换。

## 审查后再确定

- 备用连接由用户如何选择：每个主连接配置一个备用，还是每个 AgentRun 指定；是否允许跨 OpenAI-compatible 厂商。
- 哪些错误触发切换、主备各尝试几次、总时限、熔断失败阈值及冷却时间；这些直接决定延迟和费用。
- 备用失败或 Redis 熔断状态不可用时的处理方式，以及失败尝试的用量、`fallback_reason` 与实际连接如何持久化；若需新增字段，应单独确认 Schema 变更。

确认以上边界后再实现与故障注入测试；本方案不声称已具备备用模型降级或熔断能力。
