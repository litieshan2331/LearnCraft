# 四个工作流高并发承接方案

> 状态：核心实现已完成，待压测验证
>
> 日期：2026-09-24
>
> 范围：`assessment_generate`、`posttest_generate`、`plan_generate`、`card_content_generate`

## 一、结论

当前工作流生成应采用“**队列削峰、分池调度、Redis 限流、短事务持久化**”的并发方案：

1. 使用队列限制系统总并发，避免请求直接打满模型 Provider；
2. 使用 Redis 同时限制 Provider 级和用户级的并发、RPM、TPM；
3. 按工作流耗时拆分 Worker 资源池：
   - **短任务池**：`assessment_generate`、`posttest_generate`；
   - **长任务池**：`plan_generate`、`card_content_generate`；
4. 模型等待期间不持有 PostgreSQL 连接，只在领取任务、审计和写回结果时使用短事务。

当前 `infra/.env` 已将 `AGENT_REACT_MAX_TURNS_CARD_CONTENT` 配置为 `10`，Compose 默认值也已同步为 `10`，因此节点内容生成与学习路线生成都归入长任务池。

## 二、目标调用链

```text
Web 创建 AgentRun
        │
        ▼
Outbox Dispatcher 读取 run_type 并投递到对应队列
        │
        ├─ agent.run.short
        │      ├─ assessment_generate
        │      └─ posttest_generate
        │
        └─ agent.run.long
               ├─ plan_generate
               └─ card_content_generate
                              │
                              ▼
                   Worker 获取 Redis 配额
                              │
                              ▼
                 complete() 异步等待模型响应
                              │
                              ▼
                 短事务写回 AgentRun 与结果
```

队列消息继续只携带 `agent_run_id`、`trace_id` 和任务版本，不携带 Prompt、模型密钥或完整业务输入。

## 三、四项设计

### 1. 用队列限制总并发

所有生成请求继续先创建 `AgentRun`，再经 Outbox 投递到 BullMQ。Web 请求只负责受理任务，不直接调用模型。

建议将现有单一 `agent.run` 队列改为两个逻辑队列：

- `agent.run.short`：前测和后测；
- `agent.run.long`：学习路线和节点内容。

Dispatcher 在投递前读取 `run_type`，将任务路由到对应队列。短任务和长任务分别配置 Worker 副本数与单副本并发，长任务不能占满全部 Worker 资源。

总并发由以下公式控制：

```text
系统总并发 = 短任务池副本数 × 短任务单副本并发
          + 长任务池副本数 × 长任务单副本并发
```

并发值不能直接按“1000”设置，必须同时受 Provider 限额、数据库连接池、Redis 和出网代理容量约束。扩容优先采用增加 Worker 副本的方式，再根据压测结果调整单副本并发。

### 2. 增加模型调用 Redis 限流

模型调用前获取 Redis 配额，调用结束后释放并按 Provider 返回的真实用量对账。

当前最小实现使用以下限流维度：

- 全局模型调用：限制所有 Worker 合计并发；
- `api_key + model`：限制凭据和模型的并发、RPM；
- `owner_id + model`：限制用户和模型的并发、RPM。

Redis 键使用独立前缀，例如：

```text
ratelimit:model:concurrency:{provider}:{model}
ratelimit:model:rpm:{provider}:{api_key_hash}:{minute}
ratelimit:model:tpm:{provider}:{api_key_hash}:{minute}
ratelimit:user:concurrency:{owner_id}
ratelimit:user:usage:{owner_id}:{day}
```

并发许可使用原子计数或令牌桶实现。调用前先判断配额，超过配额的任务留在队列中等待或返回受控的限流错误；不能绕过 Redis 直接请求 Provider。Redis 不可用时，建议暂停新的模型调用，避免失去保护后打爆上游。

当前版本暂不做通用 TPM；备用模型单独按 Provider 返回的实际 Token 记录每日预算。

### 3. 避免四类工作流互相饿死

工作流分池如下：

| 资源池 | 工作流 | 特征 | 调度策略 |
| --- | --- | --- | --- |
| 短任务池 | `assessment_generate`、`posttest_generate` | 轮数较少、结果较小、完成较快 | 较高并发，保证交互任务及时完成 |
| 长任务池 | `plan_generate`、`card_content_generate` | 可能达到 10 轮、响应较长、持有上游请求时间更久 | 独立并发预算，避免挤占短任务资源 |

当前配置中 `plan` 默认 10 轮，实际环境中的 `card-content` 也已配置为 10 轮，因此两者都按长任务处理。即使某次任务提前完成，也只释放本池的并发许可，不影响另一池的容量边界。

两个池应分别统计队列等待时间、执行时间、重试次数、429 比例和 Token 消耗。后续可以根据实测结果独立扩缩容，例如短任务池优先保障低延迟，长任务池优先保障吞吐量。

### 4. 模型等待期间不要占用数据库连接

一次工作流执行应拆成三个阶段：

```text
领取任务：开启短事务，锁定并更新 AgentRun 状态
模型执行：不持有 PostgreSQL 连接，使用 async/await 等待 Provider
写回结果：开启短事务，写入状态、摘要、Token 和事件
```

模型等待期间允许 Node.js 事件循环处理其他 Worker 任务，但每个任务仍会占用一个受控的 Worker 并发槽和一个 Provider 并发许可。

模型出网审计、任务状态更新和最终结果写回可以短暂使用数据库连接，但必须在操作完成后立即释放，不能把连接生命周期覆盖整个 `complete()` 调用。

5. 对短任务和长任务分别进行故障注入与并发压测。

验收至少包括：

- 长任务持续堆积时，短任务仍能被处理；
- 同一用户超过并发或 Token 配额时，请求不会绕过 Redis；
- Provider 返回 429 时，重试不会突破 Provider 限流；
- Worker 扩容后，AgentRun 不重复执行；
- PostgreSQL 连接数不会随模型等待时间线性增长；
- 记录队列等待、p95 延迟、RSS、事件循环延迟、Redis 内存、Provider 429 和 Token 成本。

具体副本数与单副本并发需要以压测数据确定，不能仅凭配置值宣称已经支持某个并发规模。
